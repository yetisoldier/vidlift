# v0.4.6 — Read-Only HTTP Status API (D1 lane d)

Status: binding design 2026-10-20. Author: Bob (architect subagent). Consumers: Forge (implementation), Karen (validation). Trigger: Eric's question tonight — "would adding an API be easier?" — in response to the D1 registry-split lane options ((a) Windows-side MCP entry / (b) read-only sync / (c) document for now). Answer: **yes, and it's lane (d), and it wins.**

---

## 1. Why lane (d) wins

The v0.4.5 design §D1 compared three options for cross-machine visibility and punted with (c) "document for now." Eric's API question reframes the problem: we don't need to share the *registry* at all. We need to share what the GUI already sees.

| Property | (a) MCP on Windows | (b) read-only sync | **(d) status API** |
|---|---|---|---|
| Truth source | shared registry file | mirrored file (stale risk) | **live in-process state** |
| Dishonest-queue risk | needs write arbitration | mirror can diverge silently | **none — read-only by construction** |
| Where agents call | minipc MCP → Windows MCP | minipc MCP reads mirror | `curl http://ninjabase2:8765/status` from anywhere on the LAN/tailnet |
| New moving parts | Windows MCP install, cross-machine server policy | cron/systemd mirror, filename discipline, divergence guards | one stdlib HTTP handler in the GUI process |
| Tonight's wedged-run diagnosis | still sandboxed system.run gymnastics through LOCALAPPDATA redirects | mirror lag | **one curl** |
| Precedent | none in repo | none in repo | **shipped and proven in bluray-to-mp4** |

The wedge tonight was *visibility* — the registry JSON was invisible to the node context, and the H: drive mapping didn't survive the sandbox. An HTTP API served from the machine that owns the process eliminates the whole class of "which filesystem view am I in" problems.

**Boundary this design does NOT cross:** remote *enqueue* is untouched. It stays minipc-dev-only through the existing local MCP bridge until Eric actually asks for remote enqueue. D1's (a)/(b) debate was about reads; the API makes the read problem disappear, so (a)/(b) retire to "unnecessary unless remote enqueue is ever needed."

## 3. Endpoint spec

Minimal set, read-only by construction:

```
GET /health   → {"ok": true, "version": ..., "busy": ...}      # token-free liveness
GET /status   → full live queue snapshot                        # token-gated
GET /history  → {"jobs": [ ... ]}                               # token-gated
GET (anything else) → 404 {"error": "unknown endpoint",
                            "endpoints": ["/health","/status","/history"]}
```

Auth: `Authorization: Bearer <token>` header or `?token=` query param (sibling `_authorized`, `monitor.py:330-334`). `/health` deliberately skips auth so Eric's agents can ping liveness without the token — it exposes nothing beyond version/busy.

### 3.1 `GET /status` payload

```json
{
  "api_version": 1,
  "version": "0.5.0",
  "vidlift_version_note": "payload mirrors bridge _status_payload shape; additive keys land here automatically",
  "queue_active": true,
  "uptime_seconds": 4521.3,
  "active_jobs": [
    { "... one _status_payload per in-flight job ...": "..." }
  ],
  "queued_count": 2,
  "server_time": 1761000000.0
}
```

Each `active_jobs[]` entry is **exactly** the existing `_status_payload` dict (`tools.py:416-497`) — the contract the GUI's 1 Hz tick already consumes:

```json
{
  "job_id": "...",
  "state": "queued|running|succeeded|failed|cancelled",
  "queue_position": 0,
  "file_path": "...",
  "current_phase": "probe|plan|benchmark|upscale|encode|subtitles|...",
  "started_at": 1760999000.0,
  "finished_at": null,
  "last_activity_at": 1760999900.0,
  "log_path": "...",
  "log_tail": ["...last N lines, newest last..."],
  "commands": [...],
  "phases": [...],
  "engine_simulated": false,
  "engine_note": "...",
  "verification": null,
  "manifest_path": "...",
  "error": null,
  "progress": {
    "step": "chunk",
    "frames_done": 1200,
    "frames_total": 4800,
    "chunk_index": 3,
    "chunk_total": 12,
    "phase_note": "counting frames (no per-frame signal until done)"
  },
  "eta_seconds": 421.5
}
```

The `progress` dict is a pass-through (`tools.py:386-391` already reads `frames_done`/`frames_total` from it; v0.4.5 §3b adds `phase_note` through the same seam). **`elapsed_seconds` is derivable by the reader** (`server_time - started_at`); we don't add a computed field the GUI doesn't have. `eta_seconds` stays honest-null per the v0.4.5 anti-lie rule — never projected from a stub benchmark.

`api_version: 1` — explicit integer, bumped only on breaking shape changes. Additive keys (the repo's schema-v2 convention, same as v0.4.1's `subtitles` block) do **not** bump it.

### 3.2 Read-only enforcement argument

The handler only defines `do_GET`. There is no `do_POST`, `do_PUT`, `do_DELETE` — `BaseHTTPRequestHandler` returns 501 for those verbs by default, and that's the correct answer. The handler's only reference besides the config token is the **`LocalBridgeClient` read surface**: `status_snapshot`, `enqueue_snapshots`, `history`. It never touches `enqueue_run`, `cancel`, or `registry` write methods. Forge enforces this by construction: the server object receives a thin read-only facade (`StatusView`, defined inside `monitor.py`) wrapping the client, not the client itself. Anyone auditing sees `class StatusView` with exactly three methods.

### 3.3 Bind, port, token

- Default bind: `0.0.0.0` (LAN-visible), port **8765**, on by default — same as the sibling (`config.py:30-33`). Same port is fine: VidLift and bluray-to-mp4 don't run side-by-side in practice, and if they ever do, `start_server_with_fallback` walks ports.
- Token: `vidlift/monitor.py::MONITOR_TOKEN_DEFAULT = "vidlift-mon-<new uuid4>"` (Forge generates a fresh one; do NOT reuse the b2m token — separate blast radii). Override in the GUI settings; the setting persists via `QSettings` alongside the rest of the GUI's stored state (`gui.py:24` already imports `QSettings`).

1. **Default-on.** Server starts in a daemon thread at `MainWindow.__init__` completion (sibling: `main_window.py:383` calls the refresh after start). Startup failure is non-fatal: pill shows "Monitor off (port busy)" and the app continues.
2. **Checkbox** in the run/settings area: `"LAN monitoring (agents check upscale progress from other machines)"` — sibling text at `main_window.py:692-693` renamed. Toggled handler mirrors `_toggle_monitor` (`main_window.py:1042-1067`): on → `start_server_with_fallback`; off → `stop_server`; either way, persist via `QSettings` and refresh the pill.

4. **Token retrieval for Eric:** the pill is not the token surface (token is a secret-ish value; don't paint it on the window chrome). ## 6. Sizing and sequencing: v0.4.6, not v0.5.0

**Call: v0.4.6.** Reasons:

1. **Line count is port-scale, not design-scale.** ~220 LOC of new code, ~40 LOC of GUI diff, most of it a proven sibling shape carried over. The single genuine design decision in this doc is "don't port `MonitorState`, read the bridge client directly" — and that decision is *less* code, not more.
2. **No contract churn.** The payload is the existing `_status_payload` verbatim + an `api_version` envelope key. No schema-v2 bump, no GUI state-machine change, no runner change. Semver-wise this is a feature patch on the v0.4.x line; "v0.5.0" communicates a protocol or UX discontinuity that doesn't exist.
3. **The win is scheduling.** v0.4.5 is in flight *today*. v0.4.6 slots immediately after with no re-planning; calling it v0.5.0 invites "what else goes in the minor release" scope creep. The design doc filename stays `v0.5.0-status-api.md` only because the parent task named it that — Forge should retitle to `v0.4.6-status-api.md` on commit, or this doc can be renamed before Forge picks it up. (Recommendation: rename the file at start of implementation.)
4. **Zero conflict with in-flight v0.4.5.** Verified composition:
   - v0.4.5 touches `gui.py` (`_render_log_tail`, `run_stage_label`, `_consume_running_snapshot`), `run.py` (docstring note), `engine_ncnn.py` (heartbeat log + `phase_note` emit). This design touches `gui.py` only in `__init__` (server start, checkbox creation) and `closeEvent` — disjoint line ranges from v0.4.5's diff (v0.4.5's GUI edits are all in the polling/render path, `gui.py:763-870`; this design's edits are construction/shutdown, `gui.py:249-280` and the close handler).
   - v0.4.5's `phase_note` and frames counters ride the `progress` dict through `_status_payload` with **no bridge change** (v0.4.5 doc §7 table, "mcp_bridge/tools.py: None — the status payload gains nothing new; progress field is already a pass-through"). The API serves `_status_payload` verbatim, so the new fields appear in `/status` the moment v0.4.5 ships — **the API composes forward for free**.
   - No shared files beyond `gui.py`, and the `gui.py` hunks don't overlap.

## 7. Explicit non-goals

- **Remote enqueue/cancel over HTTP.** The handler has no write verbs and no write surface. Remote enqueue remains minipc-dev-only through the stdio MCP bridge.
- **Stuck/stalled classification server-side** (the sibling's `classify_snapshot`). Readers compute staleness from `last_activity_at` themselves; revisit only if Eric asks "make the server say 'wedged' for me."
- **Auth beyond the shared token.** No per-client keys, no TLS (LAN/tailnet trust model; Tailscale provides the encryption layer when remote).
- **Serving on the CLI.** If `vidlift mcp-server` users later want it, that's one `start_server` call in `mcp_server.main` — documented here as an easy follow-up, not in this slice.
