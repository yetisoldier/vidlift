# VidLift v0.4.0 — Decode-Truth Clock, Frame-Exact Chunking, Gate/Heartbeat/Resume

**Status:** design (port spec; no code changes in this document)
**Author:** architect (audit + port spec)
**Reference designs (read-only provenance, bluray-to-mp4 at e62a80e):**
- `bluray-to-mp4/docs/designs/v0.2.33-frame-exact-chunking.md` (".33")
- `bluray-to-mp4/docs/designs/v0.2.34-derived-stamp-rate.md` (".34")
**Implements:** Eric's 2026-10-19 directive — the v0.2.33/v0.2.34 field
lessons move into VidLift, adapted to its file-based architecture.
**Fixes:** the audit below shows VidLift's v0.3.0 engine adapter —
whose changelog advertises "frame-clock discipline" and a "15.050 s
Mamma Mia drift gate" — still stamps the mezzanine from **container
metadata** and still chunks by **wall-clock windows**. Both are the
exact lie vectors .33/.34 retired in the sibling. The advertised Mamma
Mia gate (`duration_gate` at max(0.5 s, 0.01%) against *prepared-file
format duration*, engine_ncnn.py:104-152) is the same *shape* as
v0.2.31's retired gate, not the .34 clock gate: it compares two
container-reported durations, either of which can lie in the same
direction, and it is blind to the correct-count/wrong-clock desync
that .34 caught.

## Part A — Audit of shipped VidLift v0.3.0 against the .33/.34 lessons

All line/file references verified against this repo (v0.3.0, HEAD
69ed6b7).

### A.1 What fps does the plan/engine use for chunking and stamping?

**Container metadata, end to end. Decode-truth appears nowhere.**

- `probe_frame_clock` (`vidlift/engine_ncnn.py:181-229`) resolves the
  stamp clock strictly as `avg_frame_rate` → `r_frame_rate` → named
  refusal. Both are ffprobe's parsed **container fields**. The adapter
  stamps each mezzanine segment with `-framerate clock["value"]`
  (engine_ncnn.py:738-754) — that value is the lying field verbatim
  whenever the container lies (a soft-telecine DVD-class source flagged
  30000/1001 over true 23.976 content passes VidLift's clock resolution
  cleanly, exactly the Mamma Mia shape .
  34 §0 documents).
- Chunk sizing derives from the same figure: `_run_chunks`
  (engine_ncnn.py:652-668) computes chunks from `prepared_duration`
  (a **format-duration** probe, engine_ncnn.py:232-244) and the
  metadata clock's `fps` float (`_expected_frames`,
  engine_ncnn.py:639-644).
- The probe layer (`vidlift/probe.py`) parses and reports
  `r_frame_rate`/`avg_frame_rate` but never decode-counts; there is no
  `-count_frames` call anywhere in the repo (verified by grep).
- **Drift gate placement:** two duration gates, both inside the engine
  adapter: gate P compares prepared format-duration vs the **source
  format-duration** (`plan.report.duration_seconds`); gate M compares
  mezzanine format-duration vs prepared format-duration. Neither ever
  sees a frame count or an audio-stream extent. A container that lies
  consistently (source, prepared, and mezzanine all carrying the same
  wrong clock family) passes both gates. VidLift's encode maps audio
  from the **original file** (`build_encode_command`,
  run.py:299-345: `-i mezzanine -i source -map 0:v:0 -map 1:a:0`), so
  the shipped MP4's playback clock is the source's audio timeline —
  precisely the axis no VidLift gate measures today.

**Verdict: NOT PORTED.** The v0.3.0 "frame-clock discipline" means
"never default the metadata," which was the v0.2.27-level fix. .34
proved that is insufficient.

### A.2 Time-window or frame-index chunking? What asserts chunk integrity?

**Time-window.** `_run_chunks` (engine_ncnn.py:669-700):
`start = idx * chunk_seconds; length = min(chunk_seconds, ...)`, then
extraction via `ffmpeg -ss {start} -t {length} -i prepared ... frame_%08d.png`.
No `select=between(n,...)`, no `-vsync 0`, no keyframe story. This is
the drift generator .33 §1 retired: `-ss/-t` on container timestamps
does not land on frame boundaries; per-window jitter accumulates into
feature-length drift.

The adapter's header comment (engine_ncnn.py:24-31) justifies this:
"extraction is a decode+copy; the PREPARED file already normalized
frames." That narrows *input provenance* but not *timestamp truth*: the
prepared FFV1 file's container timestamps are still what `-ss/-t`
addresses, and FFV1-in-MKV timestamps written by the prepare pass
inherit the source's clock family — including a lying one. Frame-index
addressing is the only addressing that cannot drift, regardless of how
honest the intermediate container is.

**Chunk integrity asserts today:** only *non-emptiness*
(`if not input_frames: raise`; `if not output_frames: raise`,
engine_ncnn.py:703-707, 730-734). A chunk that silently drops or
duplicates a frame **passes**, because count-vs-expectation is never
checked.

**Verdict: NOT PORTED.**

### A.2b Mezzanine reassembly gates and gate-trip behavior

- Frame-count gate (mezzanine frames == source frames): **absent**.
- Clock gate against the **audio extent** (the .34 `verify_mezzanine_clock`
  axis): **absent**. Gate M compares against prepared duration, not the
  audio that actually ships.
- Gate trip behavior: `UpscaleError` anywhere in the adapter →
  `run_file`'s `except UpscaleError` (run.py:712-733) **fails open**:
  the run completes, encoding the *prepared* (original-resolution,
  deinterlaced/normalized) file, with `fail_open`, `fail_open_reason`,
  and `engine_simulated: true` in the manifest. This fail-open contract
  matches the sibling's semantics and is the correct destination for
  every new refusal/refusal-gate this spec adds — **reused, not
  rebuilt**.
- On gate trip, the partial mezzanine path: `_run_chunks` deletes the
  output on failure (engine_ncnn.py:795-807) and the workdir is *kept*
  on failure for triage (engine_ncnn.py:787 + design Section 7). But
  when gate M trips *after* a successful reassembly, the completed
  mezzanine `<prepared>.upscaled.mkv` is left in place with **no
  diagnostic artifact**, and a retry relink-overwrites it
  (engine_ncnn.py:662-663 unlinks an existing output). The .33 §4
  retention contract (rename to `.rejected-<ts>` + diagnostic JSON) is
  not present.

**Verdict: fail-open exists and is right; gates and retention are NOT PORTED.**

### A.3 Run/status reporting during concat/verify/reassembly — blind windows?

- The run log (`RunLog`, run.py:236-252) records phase start/done events;
  `RunState.touch()` bumps `last_activity_at` at every log line and
  external command. The engine adapter reports per-chunk frame progress
  through `on_progress` (`record_progress`, run.py:700-705), so the
  upscale phase itself is observable.
- **But:** the concat step, the mezzanine clock/duration probes, the
  encode phase (`libx265` over the full runtime), and the verify phase
  (ffprobe + full `ffmpeg -f null -` decode of the entire output,
  run.py:347-385) are each **one external command** with no heartbeat
  inside. The bridge's liveness signal (`record.touch()`) bumps only on
  command *boundaries* (mcp_bridge/jobs.py:155-169). A 65-minute encode
  or a 10-minute full-decode verify reads as a frozen
  `last_activity_at` — the exact "silent-but-healthy window reads as
  stuck" lesson from the b2m field run.
- The engine's `_run_process` drains child stdout/stderr on threads and
  parses progress hints, but nothing in the ffmpeg `_ffmpeg` path
  (blocking `subprocess.run` through the seam) emits interim activity.

**Verdict: NOT PORTED (heartbeat/step-label lesson).**

### A.4 Resume capability for interrupted runs?

- Bridge registry: queued jobs resume across a server *restart*
  (registry sweep), but a job found mid-`running` at restart is marked
  **failed** (registry.py:14-21) — honest, but zero work is salvaged.
- In-run: `_run_chunks` keeps completed segments only while the process
  lives (cancel path: "completed segments stay in the kept workdir",
  engine_ncnn.py:775-778, documented for triage, not for resume). A new
  `run_file` invocation starts a fresh run_id, fresh workdir, and
  unlinks any stale output (engine_ncnn.py:662-663). No chunk-level
  checkpoint exists: a run interrupted at chunk 50/57 redoes all 50.
  Per-chunk resume is the b2m field lesson worth ~5 GPU-hours.

**Verdict: NOT PORTED.**

## Part B — Port spec

**Concepts port; code does not.** VidLift's conventions differ from the
sibling's in three load-bearing ways, and every section below respects
them:

1. **File-first, no disc/rip/title vocabulary.** All prose and symbol
   names say *source/prepared/mezzanine*, never disc/rip/title.
2. **The engine input is the prepared file**, not the source. The
   sibling derived from rip probes; VidLift derives from **prepared-file
   probes** (decode count + clock) and the **source file's shipped-audio
   extent** (the encode maps `1:a:0` from the source — run.py:323-325).
   This split is VidLift-specific and is stated precisely in B.2.
3. **The runner seam is injectable** (`Runner = Callable[[binary, args],
   (code, stdout, stderr)]`). Every new probe is a seam call with canned
   JSON in tests — the suite's established style (test_engine_ncnn.py
   boundary series b0–b12). No new subprocess discipline is invented.

### B.1 Authoritative frame count on the prepared file (ports .33 §2.1)

New helper in `vidlift/engine_ncnn.py` (the adapter owns all
engine-phase probes; probe.py stays classification-only):

```
probe_frame_count(path, *, ffprobe, runner) -> tuple[int, bool]
```

Two-pass, run once per run **inside `NcnnVulkanEngine._run_and_report`
before any chunk extraction**:

1. Fast: `ffprobe -v error -select_streams v:0 -show_entries
   stream=nb_frames -of json` (metadata only).
2. Slow (authoritative): `ffprobe -v error -select_streams v:0
   -count_frames -show_entries stream=nb_read_frames -of csv=p=0`.
   The prepared file is FFV1/MKV; a full decode-count of a
   feature-length FFV1 is minutes, not the sibling's ~30 s DVD-rip cost
   — **accepted and stated honestly**: it is still one-time, still
   pre-GPU, and still orders of magnitude cheaper than the GPU hours it
   protects. (Measured on the first real run; if it proves painful, a
   follow-up may amortize it by caching against the prepared file's
   content hash — not in this milestone.)

Selection: slow-pass `nb_read_frames > 0` is authoritative; else fast
`nb_frames > 0` with `frame_count_from_metadata=True` carried into the
diagnostic; else `UpscaleError("prepared file frame count could not be
probed")` — honest refusal, pre-GPU, routed to the existing fail-open.

### B.2 Derived stamp rate (ports .34 §1) — the VidLift-shaped derivation

**The stamp clock is derived from decode-truth, never from container
fields.** The derivation's two operands in VidLift's architecture:

- **Numerator:** `prepared_total_frames` (B.1) — the frames the
  mezzanine must reproduce exactly.
- **Denominator:** the **shipped audio's measured extent**, probed from
  the *source* file's selected audio stream — because
  `build_encode_command` maps audio from the source (`-map 1:a:0`,
  first audio stream). This is .34 §1.1's "duration of the audio
  stream that will reach the MP4," re-anchored to VidLift's encode
  shape.

New helpers in `vidlift/engine_ncnn.py`:

```
probe_audio_extent_seconds(source_path, *, ffprobe, runner) -> AudioExtent
```

- Primary: `ffprobe -v error -select_streams a:0 -show_entries
  stream=duration -of csv=p=0 <source>` (the encode always maps `a:0`;
  if VidLift later grows audio selection, the ordinal must match the
  encode map exactly, same rule as .34 §1.1(1)).
- Fallback (no audio stream, or stream duration absent): the source's
  format duration via the existing `probe_duration_seconds` — with
  `from_format=True` recorded. (VidLift permits audio-less sources:
  `_audio_plan` returns channels=0; the derivation must still behave:
  refuse only when *neither* figure exists.)
- Sanity minimums (port .34 §1.1(3) verbatim in rule): refuse when the
  chosen extent is missing, `<= 0`, `< 10 s`, or — when both stream and
  format extents exist — the two disagree by **> 25%** (broken probe,
  not a stamp source). All refusals raise `UpscaleError` → fail-open,
  pre-GPU.

**Snap** (port .34 §1.2 verbatim, including the ulp guard):

```
CANONICAL_RATES = ("24000/1001", "24", "25", "30000/1001", "50", "60000/1001")
SNAP_TOLERANCE_FRACTION = 0.001
snap_to_canonical_rate(derived: float) -> tuple[str, bool]
```

Nearest-neighbor within 0.1% relative (comparison computed as
`abs(derived - canonical) <= canonical * (0.001 + 1e-9)`; the 1e-9 ulp
guard keeps float renderings of the rationals on the right side of the
boundary). Unsnappable → `UpscaleError` naming the derived rate, both
operands, and the nearest candidate — raised **before any chunk
extraction**, fail-open in seconds.
The 50 and 60000/1001 entries stay in the VidLift set for the same
sibling reason: bwdif's field-rate arm (`build_prepare_command`'s
`sample_chain.fps_filter` / output-rate path, run.py:270-281) produces
prepared files at 50/59.94 from genuine interlace, and those must snap,
not refuse.

**Cross-provenance snap-band check (the b2m Karen finding — ported as a
first-class gate, per directive):** snapping assumes the denominator
(audio extent) is honest. Karen's counterexample: a true-23.976 film
whose audio stream *under-reports* its extent (truncated stream
duration tag — codec/container-provenance mismatch) derives slightly
fast, e.g. 163,509 frames / an under-reported 6,785 s = 24.097 → snaps
to `24`, and a duration-vs-audio clock gate computed against that same
corrupted audio extent is **blind** (both sides inherit the lie).
VidLift's defense, specified here:

1. **Two-provenance denominator rule.** When the source carries *both*
   a usable audio-stream extent and a format duration, the derivation
   runs against **both**, and the two derived rates must snap to the
   **same canonical token**; if they snap differently (the 23.976-vs-24
   band is exactly where a few-tenths-percent audio lie lands), refuse
   with both derivations named. If only one provenance exists, the ≤25%
   skew minimum (above) already cannot see a small lie — so additionally:
2. **Cross-check against the prepared file's own clock evidence.** The
   prepared file carries ffprobe container fields (which .34 demotes to
   diagnostic) *and* its own measured format duration. Compute
   `prepared_total_frames / prepared_format_duration`; if that figure
   and the audio-extent-derived figure snap to **different** canonical
   tokens, refuse, naming both provenances and both snap results. This
   is the check that catches Karen's band: under-reported audio moves
   the audio-derived snap (→24) while the prepared-container-derived
   figure stays at 23.976 — disagreement across provenance is the
   signature, and it is detectable even when each provenance is
   internally consistent.
3. When all available provenances agree on one token, that token is the
   stamp. Container `r_frame_rate`/`avg_frame_rate` remain
   **diagnostic-only fields in the diagnostic record**, never
   derivation inputs (port .34 §1.4).

The stamp token replaces `probe_frame_clock`'s avg→r resolution as the
value handed to `image2 -framerate`. `probe_frame_clock` is **not
deleted**: it keeps resolving the prepared file's declared clock for the
cross-check in (2) and for diagnostics; the *stamp authority* moves to
the derivation. (A future preparer that changes the frame count —
telecine IVTC already does via decimate — is safe by construction: the
numerator is measured on the prepared file *after* any such transform,
so the stamp matches the frames actually being reassembled. This is
VidLift's structural advantage over the sibling's rip-side derivation
and the spec states it explicitly so nobody "simplifies" it back to
source-side counting.)

`EngineResult.frame_clock` gains provenance: `{value, source:
"derived", derived_raw, snapped, audio_extent_s, audio_source,
prepared_total_frames, container_avg_frame_rate, container_r_frame_rate,
cross_provenance: [...]}` — manifest schema v2 additive extension.

### B.3 Frame-exact chunk plan and extraction (ports .33 §2.3-2.4)

In `_run_chunks`, replace the time-window math and `-ss/-t` extraction:

```
fps = stamp token float value            # from B.2
F   = max(1, round(chunk_seconds * fps)) # frames per full chunk
N   = prepared_total_frames              # from B.1
chunks = ceil(N / F)
per chunk idx: first = idx * F; count = min(F, N - first)
```

Extraction command (verified shape, port of .33 §2.4, minus the
sibling's prepare filter — VidLift's prepare already ran):

```
ffmpeg -y -hide_banner -nostdin -i <prepared> -an -sn \
  -vf "select='between(n,{first},{first+count-1})'" \
  -vsync 0 -start_number 1 <in_dir>/frame_%08d.png
```

- `-vsync 0` is mandatory (no muxer dup/drop toward an implied clock).
- `-start_number 1` keeps per-chunk PNG naming and the existing
  `_png_size(in_dir / "frame_00000001.png")` extent probe untouched.
- **Prefix-decode cost:** dropping `-ss` means chunk *k* decodes frames
  0..last(k). FFV1 intra decode is fast, but the honest statement (port
  of .33 §7(1)): chunk extraction cost grows linearly with chunk index.
  Mitigation path, deferred-exactly-as-the-sibling-deferred: an
  output-index-anchored hybrid (`-ss` to just before the chunk using
  `first / fps` seconds, then `select=gte(n, k)` with `k` derived from
  the actual frames seen) — safe to add later because frame indices,
  not timestamps, remain the authority. First real run measures
  chunk-1 vs chunk-N extraction times; if tail-chunk extraction exceeds
  ~10% of chunk engine time, implement the hybrid then.
- **Assertions (port .33 §2.4 verbatim in rule):** after extraction,
  `_count_pngs(in_dir) != count` → `UpscaleError` naming idx, first,
  count, actual; after the engine, `_count_pngs(out_dir) != count` →
  same. No partial mezzanine can assemble from a miscounted chunk.
  (The prepared file is CFR-constructed by VidLift's own prepare pass,
  so the sibling's VFR pre-flight refusal — .33 §2.2 — has no VidLift
  analog at the prepared boundary; what *does* need the check is the
  stamp, and B.2's snap-refusal covers it. Stated so nobody backports
  the VFR verdict machinery without a prepared-file VFR source, which
  VidLift cannot currently construct.)

Reassembly per chunk is unchanged except the stamp token is B.2's:
`image2 -framerate <stamp>` per segment, concat demuxer `-c copy` —
both already correct by construction once counts and clock are true.

### B.4 Reassembly gates: frames exact, clock tolerant (ports .33 §3 + .34 §3)

Two orthogonal gates run in `_run_and_report` after concat, before
returning the mezzanine:

1. **`verify_mezzanine_frames`** (new): decode-count the mezzanine
   (B.1 helper reused, slow pass) and require **exact integer equality**
   with `prepared_total_frames`. Any mismatch → `UpscaleError` with both
   counts. The FFV1 mezzanine decode-count cost equals B.1's — accepted
   (one-time, post-GPU, pre-encode).
2. **`verify_mezzanine_clock`** (new): mezzanine format duration vs the
   **audio extent from B.2** (the same provenance that derived the
   stamp), tolerance `max(2.0 s, 0.1% × audio_extent_s)` — the .34 §3
   constants, kept: kills rate-class desync (25% apart) with two orders
   of magnitude of headroom, passes legit lead-in/out skew (seconds)
   with 5× headroom. Probe failure → `UpscaleError`, honest refusal.

Gate P (prepare-vs-source) and gate M's current form are **retired as
stamp authorities but kept as diagnostics**: their record still lands in
`duration_gates` (manifest compat), but gate M's prepared-duration
reference is superseded by the audio-extent clock gate. Gate P keeps
its refusal behavior (a prepare-phase clock bug must still abort
pre-GPU) — with one fix: its reference (`plan.report.duration_seconds`,
a format duration) is fine as a *sanity* check, but the manifest record
must label it `format_duration`, and the new `duration_gates` payload
gains the clock-gate record keyed `mezzanine_vs_audio` beside the
existing `mezzanine_vs_prepared`.

Either new gate trip → `UpscaleError` → the **existing** fail-open
(run.py:712-733) ships the synchronized original-resolution encode.
No runner changes to the fail-open path.

### B.5 Rejected-mezzanine retention + diagnostic (ports .33 §4/.34 §4)

On `UpscaleError` *after* a mezzanine file exists (gate trips and any
late adapter failure), the adapter — before the exception crosses the
runner seam:

1. Renames `<prepared>.upscaled.mkv` →
   `<prepared>.rejected-<ISO8601>.mkv` (same directory). Never deletes.
   The workdir-retention contract (design Section 7) already covers the
   chunk dirs; this covers the assembled artifact.
2. Writes `<prepared>.rejected-<ISO8601>.diagnostic.json` with:
   `source_path`, `prepared_path`, `prepared_total_frames`,
   `frame_count_from_metadata`, `audio_extent_s`, `audio_source`
   (`stream`/`format`), `derived_rate_raw`, `derived_rate_snapped`,
   `stamp_fps`, `container_r_frame_rate`, `container_avg_frame_rate`,
   `cross_provenance` results, `chunk_frames`, `chunks`,
   `expected_per_chunk` (list of ints), `mezzanine_frame_count` (when
   probeable), `mezzanine_duration_s`, `clock_tolerance_s`, `error`.
3. The `UpscaleError` message gains: "rejected mezzanine retained at
   \<path\>; diagnostic at \<path\>". The runner's fail-open logging
   (`fail open reason:` line, run.py:731-732) carries it verbatim into
   the log and manifest — no runner signature change.

### B.6 Heartbeat + step labels in long phases (field lesson)

The liveness contract: **`last_activity_at` must advance at least every
30 s during any phase that can exceed ~2 minutes**, and the status
payload must name *what* is running, not just the phase.

- **Engine adapter (concat + gates):** `_run_chunks`' concat step and
  both new gate probes wrap in labeled steps that log through the
  adapter's existing `_log` and fire a lightweight
  `on_step(label: str)` callback (new optional kwarg on
  `EngineAdapter.run`, defaulting None). The runner's `record_progress`
  seam gains a sibling `record_step(label)` that sets
  `state.progress["step"] = label` and touches the state. Steps:
  `concat`, `gate-frames-probe`, `gate-clock-probe`. The two
  decode-count probes (B.1 pre-GPU, B.4 mezzanine) also heartbeat: run
  the probe on a thread and touch every 5 s, or, simpler and preferred,
  use `ffprobe -progress` on a pipe and touch per progress line.
- **Encode and verify phases (runner):** the blocking
  `run_command`/`verify_output` calls gain the same heartbeat wrapper.
  Implementation: run the subprocess through a small pump that
  polls every 5 s, calls `state.touch()`, and — when the tool emits
  parseable progress (`-progress pipe:1` for encode; none for full
  decode — touch-only there) — updates `state.progress` with
  `encode_seconds`/`decode` hints. `run_command`'s signature gains an
  optional `heartbeat: bool = False` flag so callers opt in per long
  command (encode, full decode, the two count probes); short probes
  keep the cheap blocking path.
- **Bridge:** no protocol change — `status` already reports
  `last_activity_at`, `current_phase`, `progress`; the heartbeat makes
  those fields *true* during the previously-blind windows. The
  `infer_phase` map (jobs.py:104-124) gains the count-probe shapes
  (they carry `-count_frames`) → `upscale` phase attribution.
- Step labels appear in the run log lines (`phase encode: heartbeat
  t=320s` style, one line per touch interval throttled to 30 s max
  write rate) so the log tail alone disproves "stuck."

### B.7 Per-chunk resume (field lesson)

Scope: resume within the **upscale phase of one file** after process
death or cancel; not cross-phase, not a general job checkpoint system.

- The engine workdir (`<run_id>.engine-work`) already survives failure.
  Add a checkpoint file `chunk_state.json` in the workdir, fsynced
  after each chunk completes:
  `{stamp_fps, prepared_path, prepared_total_frames, chunk_frames,
    completed: [{idx, count, segment: "<name>", segment_sha1_or_size}],
    params: {model, tile, scale, chunk_seconds}}`.
- On entry, `_run_chunks` looks for a checkpoint whose `params` and
  `prepared_total_frames` (cheap parts: total frames + stamp token must
  be re-derived fresh, and equality proven before reuse) match the new
  invocation. **Any mismatch → the workdir is stale: delete it
  wholesale and start clean** (no partial-trust). On match, verify each
  recorded segment file exists with its recorded size (cheap integrity;
  not a hash — FFV1 segments are deterministic outputs of verified
  chunks, and the gate pair in B.4 remains the real tripwire), then
  skip those chunks entirely and concat from all segments. Completed
  segments must also be *probed* cheaply (`probe_duration_seconds`
  per segment ≈ instant on MKV) to refuse a truncated write from a
  kill-mid-segment: duration must equal `count / stamp_fps` within one
  frame-time.
- Cancel-mid-chunk semantics are unchanged: partial `in`/`out` dirs are
  cleaned, the interrupted chunk is simply absent from `completed`.
- Retry entry point: the runner does not change; `run_file` on the same
  input naturally re-prepares (cheap relative to GPU) and the engine
  finds its checkpoint. The bridge's restart-sweep keeps marking
  interrupted jobs `failed`; the *retried* job is a new job that
  inherits the old workdir only when the operator retries with the same
  `log_dir`+file — documented in the spec text so nobody expects
  automatic cross-job resume.
- Chunk engine processes are the GPU hours; extraction and reassembly
  redos for un-checkpointed chunks are accepted (correct by the B.3
  assertions regardless).

### B.8 Manifest schema v2, additive

`duration_gates` gains `mezzanine_vs_audio`; `frame_clock` becomes the
provenance dict of B.2; new top-level run fields (all optional,
defaulting absent/None): `frame_gates: {mezzanine_vs_prepared:
{expected, actual, ok}}`, `resume: {checkpoint_used: bool,
chunks_reused: int}`, `rejected_mezzanine: {path, diagnostic_path}`
(when retention fired). Every existing v2 field is unchanged.

### B.10 Risks

1. **FFV1 decode-count cost** (B.1 and B.4 on feature-length prepared
   files/mezzanines) is the real, new wall-time cost — minutes each.
   Accepted as the price of truth; measured on the first real run; the
   spec forbids silently degrading to metadata-only counts (that is the
   lie vector returning through a performance door). If measurement
   forces relief, the honest relief valve is a content-hash-keyed cache
   of the prepared count, documented and flagged in the manifest.
2. **Prefix-decode extraction growth** (B.3 note) — tail chunks decode
   the whole prefix. The hybrid-seek optimization is explicitly
   deferred with its correctness-preserving proof (indices stay
   authoritative); do not implement it in this milestone.
3. **Cross-provenance refusal may fire on legitimately odd files** (a
   source whose audio genuinely ends early — commentary-only rips).
   Refusal is fail-open and cheap (pre-GPU); the diagnostic names both
   provenances so the operator can see *why*. Chosen over silent
   stamp-guessing, per the sibling's "honest no in seconds" contract.
4. **Heartbeat pump complexity** in `run_command` touches the runner's
   most-trusted path. Mitigation: opt-in flag, no new threads for
   short commands, and the pump is a poll loop (not signal/callback
   machinery) with the same terminate/kill discipline the engine
   already uses on cancel.
5. **Resume checkpoint trust.** Size+duration integrity is deliberately
   cheap, not cryptographic; the B.4 gates remain the authoritative
   tripwire, so a corrupt-but-plausible segment still fails the exact
   frame gate. Params-mismatch wholesale-delete keeps stale-cache
   poisoning impossible by construction.
6. **Audio selection rigidity.** Encode maps `a:0` today
   (run.py:323-325); B.2 probes `a:0`. If audio selection ever becomes
   configurable, the probe ordinal must follow the encode map or this
   spec's clock is silently wrong — pinned as a comment requirement at
   both seams.

### B.11 Out of scope (scope discipline, stated)

- No backport of the sibling's disc concepts (disc/rip/title/makemkv)
  in any form. No VFR verdict machinery (B.3 note). No audio-stream
  selection feature. No changes to prepare/classify/encode geometry or
  bitrate planning. No GUI work. No bridge protocol version bump (all
  payload additions ride existing fields). No benchmark-constant
  changes. The b2m `.33/.34` code itself is reference-only; every
  landing here is written against VidLift's seams.

**Bottom line:** v0.3.0's advertised clock discipline is metadata
hygiene, not decode-truth. The Mamma Mia 15.050 s fixture pinned in the
v0.3.0 suite (`test_b3_mamma_mia_drift_shape_rejects_at_gate_m`) guards
a gate that compares prepared-vs-mezzanine container durations — it
catches *inconsistent* drift but cannot catch a consistently lying
clock family, and it never involves the audio that actually ships. This
spec ports the truth: count the frames, measure the audio that reaches
the MP4, snap or refuse, chunk by index, gate twice (exact counts,
tolerant clock), retain rejects, and keep the monitor loudly alive.
