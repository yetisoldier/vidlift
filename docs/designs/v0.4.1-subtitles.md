## Part A — Sub-audit of VidLift today (HEAD 69ed6b7)

All line references verified against the checked-out tree (== HEAD;

### A.1 What does the encode map today? Are subs dropped? Sidecars seen?

`build_encode_command` (`vidlift/run.py:437-480`):

- **Audio comes from the source file, video from the mezzanine** —
  `-i mezzanine -i source -map 0:v:0 -map 1:a:0` (run.py:458-466; the
  v0.4.0 audit's "1:a:0 from source" flag at its §A.1/bullet 4 refers to
  this map at run.py:466, cited there as 323-325 in pre-refactor
  numbering — verified same line content).
- **Text subs:** mapped as `-map 1:s?` with `-c:s mov_text`
  (run.py:467-468, 477-478) — *but only when every probed subtitle
  stream is text*: `carry_subs = bool(text_subs) and
  all(s.kind == "text" for s in report.subtitles)` (run.py:455-456).
- **The drop rule, verbatim from the docstring (run.py:449-452):**
  *"all subtitle streams map only when every one is text; mixed
  text/image files carry none (image subs are never OCR'd and mov_text
  cannot hold them)."* So:
  - A file with **any image sub** (PGS/VobSub/XSub/DVB) — even alongside
    a perfectly good English SRT track — ships with **zero subtitles**,
    silently (only the plan's `subtitle_note` mentions it;
    `plan.py:_subtitle_note`, line 147-161, says *"N image stream(s)
    listed only; no OCR in VidLift"*).
  - **All-bitmap sources** (the DVD-rip class VidLift exists for —
    `SOURCE_DVD_MPEG2_RIP` in probe.py) always ship subtitle-free.
- **External sidecars: never looked at.** A repo-wide grep for `sidecar`
  / `.srt` outside tests and docs finds **zero** hits in `vidlift/*.py`.
  `movie.srt` next to `movie.avi` is invisible to probe, plan, and run.
- **Probe does detect and type embedded subs correctly already** —
  `probe.py:65-73` classifies `subrip/srt/ass/ssa/mov_text/webvtt/text`
  as `text`, `dvd_subtitle/vobsub/pgssub/hdmv_pgs_subtitle/dvb_subtitle/
  xsub` as `image`, anything else `other`, and carries the stream's
  language tag (`SubtitleInfo.lang`, probe.py:113-121, 261-269). The
  detection foundation is built; only disposition is missing.

**Verdict: text-only pass-through exists but is all-or-nothing; bitmap
subs are silently dropped; sidecar adoption does not exist. This is the
gap v0.4.1 closes.**

### A.2 Output container and format constraints

- Output is **MP4 only**: `_expected_output_path`
  (`plan.py:131-135`) pins `<stem>.vidlift.720p.hevc.mp4`; the encode
  adds `-movflags +faststart` (run.py:479). MP4's only legal soft-sub
  codec is **mov_text** (tx3g is the same thing by another name; see
  b2m v0.2.16-embedded-subs §1 — no second candidate exists, so there
  is no codec decision to make, only an embed decision).
- **Manifest schema v2** (`run.py:_build_manifest`, 1042-1102) imposes
  no constraint — it is additive by convention (v0.4.0 §B.8 extends it
  the same way this spec does). The manifest already carries
  `plan.subtitle_note` (run.py:1097) — a free-text field v0.4.1
  upgrades into structured data (Part B.7).
- Verify (`verify_output`, run.py:398-481) checks existence,
  decodability, full decode, and geometry — nothing about subtitle
  presence. v0.4.1 adds a subtitle assertion to verify (B.5), honestly
  scoped.

### A.3 Platform targets → the OCR engine story per platform

VidLift runs in two places (docs/design.md:154-181, roadmap.md:94-104):

1. **This Linux dev box** (pipeline correctness),
2. **Eric's Windows box** (3090 Ti throughput, TV playback acceptance;
   a packaged Windows app is roadmap item 7).

The proven b2m OCR stack is Windows-shaped: seconv is a Windows CLI
binary (SeConv-Windows-x64.zip, build-windows.yml:43-50) driving a
bundled Tesseract 5.5.3 (build-windows.yml:55-68). Tesseract itself is
cross-platform; **seconv is not** (Subtitle Edit is .NET; seconv on
Linux under Mono is unproven and out of scope).

**Decision (v0.4.1 engine story):**

| Platform | Bitmap-sub OCR engine | Packaging |
|---|---|---|
| **Windows (packaged app)** | **seconv + bundled Tesseract + bundled eng.traineddata** — the b2m payload, bit-for-bit: same zips, same staged layout `tools/SubtitleEdit/{seconv.exe,Tesseract/…}`, same post-build presence gates (build-windows.yml:161-168 ported). | Bundle, exactly as b2m does. The lessons are load-bearing: refuse the GUI binary (`_refuse_gui_binary`, subtitles.py:118-131 — run 12's wizard); seed the settings JSON; pin `/outputfilename`; `/ocrlanguage:eng` (the ISO 639-2 "en vs eng" lesson, subtitles.py:77-84 + docstring); purge stale pass-1/pass-2 SRTs before each pass (v0.2.29). |
| **Linux (dev box)** | **Direct Tesseract rasterization path**: ffmpeg renders the bitmap track to PNGs (`-c:s png` image2 muxer, timed via the extracted single-track MKV's timestamps), `tesseract <png> stdout -l eng` per image, cues assembled from track timestamps. No seconv, no Mono, no new dependency beyond the `tesseract` binary which VidLift resolves the same explicit way as ffmpeg (`VIDLIFT_TESSERACT` env → PATH → named `MissingToolError`-class failure, **not** silent). Rationale: the dev box's job is pipeline correctness (design.md:178-179); a seconv-under-Mono port is unvalidated surface area for zero correctness gain. | System/venv tool, explicit resolution, no bundling in v0.4.1. |
| **Any platform with no usable OCR tool** | **Fail open with an honest warning** (the b2m pattern, CHANGELOG 0.2.27 fail-open bullet): the run ships video+audio, the warning names the missing tool and exactly what to install, the manifest records `subtitles.status: "failed-open"` with the reason. Never refuse the run: subtitles must never block a completed upscale (Eric's standing fail-open philosophy; b2m pipeline.py's `except SubtitleOcrError` → warning-and-ship contract). | — |

**Explicitly rejected:** porting seconv to the Linux lane via Mono in
v0.4.1 (unvalidated; the direct-Tesseract path covers the dev box's
correctness role; if Eric wants Linux OCR parity later it is an additive
engine lane, not a redesign). Also rejected: making OCR absence a run
refusal — b2m proved fail-open is the right contract (a missing subtitle
is recoverable; a blocked 5-hour upscale is not).

## Part B — Design

**Concepts port; code does not** — same rule as v0.4.0. VidLift-shaped
adaptations respected throughout:

1. **File-first, no disc/rip/title vocabulary.** Sources are *files*;
   there is no disc scan, no MakeMKV, no recommendation-over-sids.
   Subtitle selection is therefore *probe-driven*, not scan-driven
   (B.2).
2. **The runner seam is injectable** (`Runner = Callable[[binary, args],
   (code, stdout, stderr)]`, run.py:69-71). Every new external call —
   extraction, seconv, tesseract, mux — goes through this seam; tests
   replay canned results, suite style (test_run.py/test_engine_ncnn.py
   boundaries).
3. **Phases and observability already exist** (`PHASE_ORDER`,
   run.py:78-87; `record_step`/heartbeat land with v0.4.0 §B.6).
   Subtitle work slots into the phase list additively (B.4).

### B.1 Probe: embedded-stream detection + sidecar adoption

**Embedded streams — already 90% there** (A.1): `probe.py` types every
embedded sub. v0.4.1 additions, all additive to `FileReport`
(probe.py:139-158):

- `SubtitleInfo` gains an `index: int` field — the ffprobe stream index,
  required for extraction `-map 0:N`. (Today the probe drops it; b2m's
  `extract_subtitles(mkv_path, stream_index, …)` contract
  (subtitles.py:96-135) needs it.)
- **Bitmap-sub disposition decision at probe time**: a stream is an OCR
  *candidate* iff its codec is in the handled bitmap set
  (`hdmv_pgs_subtitle`, `dvd_subtitle` / `vobsub`). `dvb_subtitle`,
  `xsub`, and `other` are detected and honestly reported as *uncarried*
  (they are rare in VidLift's SD-file target set; handling them is a
  follow-up, stated in B.9).

**Sidecar adoption rule (new):** when the probe finds **no embedded
text sub and no carry-worthy text situation** (i.e., no `kind == "text"`
stream at all), VidLift looks next to the source for a same-stem
sidecar, once, in this order:

1. `<stem>.srt` — adopted as the pass-through text track.
2. `<stem>.sub` + `<stem>.idx` (VobSub pair) — adopted as an OCR
   *candidate* **of last resort** (see timing caveat, B.6 — sub/idx is a
   frame-number-adjacent format family).

Rules: same directory, exact stem match (case-insensitive on Windows,
exact on Linux), first match wins, a found sidecar is recorded in the
report as `sidecars: [{path, kind}]` (additive `FileReport` field).
Adoption is **reported, never silent** — the probe report and plan name
the adopted file. A sidecar alongside a source that *does* have embedded
subs is noted but not used (embedded truth wins; the note prevents
surprise when the player's auto-load picks the disk file).

**Not adopted:** ASS/SSA *sidecars* in v0.4.1 (embedded ASS passes
through per B.3, but hunting for loose `.ass` files is scope creep —
stated for the scope ledger). Strange stems (`movie.English.srt`,
`movie.eng.srt`) are not globbed in v0.4.1 — one exact `<stem>.srt`;
multi-language sidecar discovery is a follow-up (B.9).

### B.2 Track selection (file-first replacement for b2m's recommend)

b2m's `recommend.py` selects over a disc scan; VidLift has files. The
 Eric-approved philosophy (English subs included by default, players can
toggle off — recommend.py:184-189; commentary/descriptive skipped —
recommend.py:112-115) ports as a deterministic probe-side rule:

1. If any embedded **text** sub exists → the *first* text stream is the
   pass-through track. Preference within ties: `lang in ("eng", "en")`
   first, then lowest stream index. (b2m's `_is_english`,
   recommend.py:46-48, verbatim in rule.)
2. Else if any embedded **handled-bitmap** sub exists → the *first*
   PGS/VobSub stream is the OCR candidate (English-tagged first, same
   tie-break). One stream only: v0.4.1 OCRs a single track (b2m does
   exactly one; multi-track OCR is B.9 follow-up).
3. Else the adopted sidecar (B.1), if any.
4. Else: no subtitles — the plan records `none` and this is **not** a
   warning, just a fact (Eric's files aren't guaranteed to have subs;
   the honest `none` already exists in `_subtitle_note`).

The selection lands in the plan (B.7 payload) so the run phase has no
decision logic at all — plan-time decisions, run-time execution, the
repo's established split (`build_file_plan` vs `run_file`).

### B.3 Text subs: pass-through path (no OCR)

For embedded text subs and adopted `.srt` sidecars:

- **Embedded text:** the existing encode map (`-map 1:s? -c:s
  mov_text`, run.py:467-478) stays, with **one behavioral fix**: the
  all-or-nothing `carry_subs` gate (run.py:456) is replaced by a
  *selected-track* map — the chosen text stream maps by explicit index
  (`-map 1:<idx>`), so a mixed text+bitmap file now ships its text track
  (dropping today's silent mixed-drop, A.1). mov_text conversion of
  SRT-in-MKV/MP4/AVI is ffmpeg-native.
- **Style loss acknowledged honestly:** ASS/SSA styling (fonts,
  positioning, karaoke) does **not** survive mov_text conversion; the
  plan note says so for ASS sources (matches b2m's "basic, no styling
  preservation" philosophy; mov_text carries plain text + timing only).
  This is stated, not hidden.
- **Adopted `.srt` sidecar:** muxed post-encode with the proven
  b2m pattern — `mux_srt_into_mp4`'s temp-sibling-then-`os.replace`
  atomicity (subtitles.py:469-534; v0.2.16-embedded-subs §2: a failed
  mux leaves the MP4 **bit-identical**). Ported to VidLift's runner
  seam, using the source-sidecar path as input 1.
- **`.srt` sidecar disposition: KEEP alongside the MP4** — b2m's
  Eric-approved default (v0.2.16-embedded-subs §1 "Sidecar disposition:
  KEEP"): embed mov_text in the MP4 **and** write/copy
  `<output-stem>.srt` next to it. Editable, players auto-load either,
  costs nothing. For an adopted sidecar this is a copy; for an extracted
  embedded text track, ffmpeg transcodes the stream to a sidecar SRT at
  encode time (`-c:s srt` second output, one extra cheap pass — or a
  post-pass `-c:s copy`-to-srt; implementation choice, both trivially
  seam-runnable).

**Language tagging:** the embedded track's
`-metadata:s:s:0 language=` uses the ported `mux_language` rule
(subtitles.py:458-466): `eng`/`en` → `eng`, everything else **including
empty** → `und` — never stamp `eng` on an unconfirmed stream (the
honesty rule from v0.2.16-embedded-subs §3).

### B.4 Bitmap subs: the OCR pipeline (port of v0.2.27 + v0.2.29 + v0.2.30)

New module **`vidlift/subtitles.py`** (mirrors b2m's module boundary;
the runner imports it, keeping run.py thin — the same argument as
v0.2.16-embedded-subs §1 "Placement"). Flow, with b2m citations per
step:

1. **Extract the selected bitmap stream losslessly** from the *source*
   file (subs never enter the prepared/mezzanine path — the encode maps
   audio+subs from the source today, and OCR input is the source's own
   track): `ffmpeg -map 0:<idx> -c copy <intermediate>` — PGS → `.sup`,
   VobSub → **single-track `.mkv`** (the v0.2.16-vobsub-ocr §2 branch:
   ffmpeg has no vobsub muxer; matroska is the only container that
   takes a `dvd_subtitle` copy; `_intermediate_ext`,
   subtitles.py:439-455). Port the same-directory-collision guard
   (subtitles.py:526-543 — v0.2.16's "Output same as Input" real-ffmpeg
   lesson).
2. **OCR** per platform engine (A.3):
   - **Windows / seconv lane:** the v0.2.27 two-pass unattended flow,
     ported exactly: settings seed
     (`write_ocr_settings`, subtitles.py:137-158 — the conservative
     libse line/duration contract, pinned keys so seconv never warns);
     pass 1 raw OCR with pinned `/outputfilename`, `/ocrlanguage:eng`,
     `/settings:` (subtitles.py:286-307); **stale-file purge before each
     pass** (subtitles.py:356-370 — v0.2.29, the "different title's
     subtitles under a success path" poison); pass 2 FixCommonOcrErrors
     auto-resolve with `/fce-language:en` (subtitles.py:309-329);
     pass-2 failure falls back to the raw SRT with an honest note
     (subtitles.py:374-377, 600-612); **truncated pass-2 parse falls
     back to raw** (subtitles.py:582-603 — v0.2.29's second fix);
     auto-resolved cue count reported by **timing-paired** diff
     (`_count_auto_resolved_cues`, subtitles.py:186-211 — Karen's
     v0.2.30 zip-drift fix, ported as-is).
   - **Linux / direct-Tesseract lane:** render track bitmaps to PNG via
     ffmpeg (`-c:s png` image2 sequence against the extracted
     single-track MKV; frame timestamps come from the container), OCR
     each PNG with `tesseract <png> stdout -l eng --psm 6`, and assemble
     cues. This lane is new code (seconv does this orchestration on
     Windows); it reuses the same downstream: parse → normalize →
     quality note → sidecar/mux/kit. Its correctness bar is the same
     fixtures (E-series tests) with a stubbed runner; its real-media
     validation is the dev-box lane of the test plan (C).
   - **Both lanes share everything downstream of "SRT text in
     memory"**: `parse_srt`/`normalize_cues`/`write_srt_file` ported
     from `bluray_to_mp4/srt.py` verbatim (99 lines, header documents
     the deliberate conservatism — fix numbering/timestamps/artifacts,
     never touch cue text).
   - **Zero-cue = OCR failure** (subtitles.py:607-612): never silently
     ship an empty SRT; raises `SubtitleOcrError`-class → fail-open.
3. **Quality reporting — the v0.2.30 honesty kit, ported verbatim in
   rule:**
   - The deterministic quality line over the shipped text:
     `_ocr_cue_quality`/`_ocr_quality_note` (subtitles.py:214-270) —
     clean/garbage/empty counts, the documented conservative character
     contract (ASCII + basic punctuation + accented Latin-1 minus ×÷
     plus Ÿ; curly quotes/pipes/cent signs count garbage — the shape of
     Tesseract misreads on stylized fonts). **Reporting only, never a
     gate** — a garbage-heavy result still ships; the note says so.
     (Eric's 2026-10-04 report that spawned v0.2.30 was silent
     poor-quality text; the line exists so that can never be silent
     again.)
   - The `<output-stem>.ocr/` **diagnosis kit** next to the MP4,
     written on **success AND fail-open**
     (`_write_ocr_diagnostic_kit`, subtitles.py:273-330; the fail-open
     write at subtitles.py:616-630): the extracted bitmap track
     (size-capped at 150 MB, skip-with-note above —
     `_OCR_TRACK_CAP_MB`, subtitles.py:276-279) and the raw pass-1 SRT
     as `<stem>.raw.srt`, **always** in a subfolder (a bare raw .srt
     sibling would make every player auto-load uncorrected text over
     the shipped sidecar — subtitles.py:294-298). Retention degrades
     to notes on OSError, never errors (subtitles.py:328-329).
   - The auto-resolved-count note wording ported verbatim in spirit:
     always named (including 0 — proves pass 2 ran), spot-check wording
     above zero (subtitles.py:636-655); the <50-cue sanity note
     (subtitles.py:659-662); the standing "Tesseract is ~95-99%
     accurate; spot-check" closer (subtitles.py:663).
4. **Ship:** normalize → `<output-stem>.srt` sidecar → mov_text mux
   into the finished MP4 (temp-then-replace, B.3) with
   `mux_language` tagging. The embedded track and the sidecar are the
   same normalized text; the `.ocr/` kit holds the raw for offline
   tuning (no re-rip/re-encode needed to re-tune — the v0.2.30
   motivation).

**Where OCR runs in the phase list:** a new `PHASE_SUBTITLES =
"subtitles"` between `PHASE_VERIFY` and `PHASE_DONE`. Placement
rationale: OCR operates on the *source* file but muxes into the
*finished MP4*, so it must run after encode; after verify keeps
verify's scope purely A/V structural (B.5 adds a cheap subtitle
assertion to it rather than reordering). The phase is **optional by
presence** — no selected track → phase records `skipped` and ends in
milliseconds. Long-window observability: OCR of a feature-length bitmap
track is minutes of child-process time — it runs under v0.4.0 §B.6's
heartbeat/`record_step` machinery (seconv prints progress lines;
tesseract-per-image gives natural per-image steps). Prerequisite cited,
not respecified.

### B.5 Verify integration (cheap, honest)

`verify_output` (run.py:398-481) gains one additive check: when the
plan selected a subtitle track, the output probe's stream list must
contain a `codec_type=subtitle, codec_name=mov_text` stream; when none
was selected it asserts none (guards against a stray map). A subtitle
mismatch is recorded in the `VerificationResult.to_dict()` extension
and lands as a **run warning, not a verification hard-fail** — subtitle
loss must not fail an otherwise-good 5-hour upscale (fail-open
philosophy; Eric approves this asymmetry explicitly: A/V integrity is
gating, subtitle presence is reporting).

### B.6 Timing integrity — the invariant that makes this not-a-bolt-on

**The invariant:** SRT/mov_text subtitles are wall-clock timed;
VidLift's output preserves the source's wall-clock duration *by
construction* once v0.4.0's decode-truth clock gates exist. Concretely:

- v0.4.0 §B.2 derives the mezzanine stamp as
  `prepared_total_frames / shipped_audio_extent`, snapped to a canonical
  rate; §B.4 gates the mezzanine clock against that audio extent at
  `max(2.0 s, 0.1%)`. The encode then maps the **source's** audio
  stream unchanged (`-map 1:a:0`, no `-c:a` retiming, no speed filter).
  Net effect: shipped MP4 duration == source audio extent, within the
  gate tolerance — far inside subtitle-perceptible skew.
- **Guarantee for subs:** any subtitle track timed against the source's
  timeline (embedded subs are; a same-stem sidecar shipped with the
  source is by authoring) is timed against the output's timeline.
  **No re-timing, no offset, no stretch is needed or permitted** — the
  spec forbids adding retime machinery precisely because the clock
  invariant makes it unnecessary. (This is the payoff of doing v0.4.1
  after v0.4.0, on its seams, per the sequencing directive.)

**Edge cases flagged honestly:**

1. **Frame-number-based formats.** MicroDVD (`.sub` in text
   MicroDVD form) and the VobSub `.sub/.idx` pair index cues by
   frame/rate family, not pure wall clock. A `<stem>.sub` sidecar
   adopted under B.1 requires a rate-aware conversion to SRT using the
   **v0.4.0 derived stamp rate** (the same canonical token the
   mezzanine uses — subtitles and video then agree by construction).
   If the stamp refused in v0.4.0 (unsnappable → fail-open at
   original resolution), the wall-clock invariant still holds (the
   fail-open encode is also duration-preserving: prepared file
   re-encoded with source audio), and sub/idx adoption converts with
   the *prepared container's declared rate* — with an honest note that
   the rate is container-derived (the v0.4.0 demotion rule applies to
   pixels, not to this one-time conversion; stated so nobody
   re-litigates it). Embedded VobSub/PGS are wall-clock-true after
   OCR (seconv reads the container timestamps; the settings seed pins
   `currentFrameRate`/`defaultFrameRate` 23.976 only for
   frame-number-invocable formats, subtitles.py:143-144 — ported).
2. **Prepare-phase speed changes: audited, none beyond the known
   two.** `build_prepare_command` (run.py:295-344) can alter the
   *frame count* via IVTC decimate (24000/1001 out) or bwdif field-rate
   doubling (50/59.94 out) — both change the **frame timeline, not the
   wall-clock timeline** (IVTC restores film rate at the same playback
   duration; bwdif keeps duration while doubling frame count). Neither
   touches audio; the audio extent is the clock reference (v0.4.0
   §B.2). **No transform in the prepare phase alters wall-clock
   duration** — verified across the filter chains in
   `classify_sample.py` and run.py:295-344. Since subs are sourced
   from the *source file* (never the prepared file) and the output
   duration tracks the source audio, the wall-clock invariant is
   unaffected by prepare-phase frame surgery. This is VidLift's
   structural advantage over b2m-styled rip-side reasoning, the same
   one v0.4.0 §B.2 states for stamps.
3. **PAL-speedup sources** (`pal_speedup_suspected`, probe.py) already
   carry a same-timeline subtitle track (PAL releases ship PAL-timed
   subs); the warning stays an expectation-setting note, no sub
   impact. Mismatched-source sidecars (an NTSC-timed .srt next to a
   PAL file) are undetectable at this scope — noted as a known
   limitation, not papered over (B.9).

### B.8 Fail-open semantics (the contract, one place)

Every subtitle failure lands in exactly one bucket:

- **No subs found** → `status: "none"`, no warning (fact, not failure).
- **OCR impossible** (no engine on platform, tool missing) → honest
  warning naming the tool + fix; `failed-open` in manifest; video+audio
  ship normally. The run's `ok` is untouched.
- **OCR hard-fail** (extraction fail, zero cues, invalid unrecoverable
  SRT) → same fail-open; the `.ocr/` kit is still written (b2m's
  rule: a bad-OCR source must be re-tunable without re-work —
  subtitles.py:616-630).
- **Mux fail** → sidecar kept, MP4 bit-identical (temp-then-replace),
  warning distinguishes "embed failed; sidecar kept" from "no
  subtitles" (the v0.2.16-embedded-subs §2 wording lesson).
- **Never:** a subtitle failure fails the run, blocks the upscale, or
  converts to a RunError. (`UpscaleError`'s clause-d fail-open is the
  *engine's*; subtitles have their own, lighter contract — no
  synchronization risk exists for soft subs, so there's nothing to
  gate.)

### B.9 Out of scope (scope discipline, stated)

- **Hardcoded/burned-in subs: out of scope.** Detection alone is
  unreliable (they are pixels; nothing in the container marks them) and
  extraction is OCR-of-the-video-frame with no cue structure — a
  research project, not a feature. Stated so nobody promises it.
- **No translation** (English-only OCR per Eric's b2m default; a
  non-English tagged bitmap track is still OCR'd through Tesseract-eng
  with an honest `und` tag + warning — matching b2m's philosophy where
  OCR hard-codes eng and tags honestly, subtitles.py:464-465 + mux
  rule; **deviation for Eric's approval**: none proposed — VidLift
  follows the b2m default exactly).
- **No styling preservation beyond basic** (mov_text is plain text;
  ASS style loss acknowledged in B.3). **No subtitle editor UI** (the
  `.srt` sidecar + `.ocr/` kit *is* the edit surface — tune offline,
  remux by hand or re-run).
- **Not in v0.4.1** (parked, noted): multi-track OCR, non-English
  language packs, glob-style sidecar discovery, ASS sidecar adoption,
  Linux seconv-via-Mono, dvb/xsub OCR, subtitle-sync tooling, VFR
  sources (already refused upstream by v0.4.0's prepared-file
  construction).

### C.4 Risks

1. **Linux direct-Tesseract lane is new orchestration code** (seconv
   normally owns bitmap→cue assembly). Mitigation: it shares every
   downstream check with the proven lane (S13 pins parity), dev-box
   validation covers correctness, and Windows — Eric's production lane —
   runs the twice-field-proven seconv stack. If the lane proves fragile,
   disabling it still leaves Windows fully featured by design.
2. **OCR quality remains Tesseract-bound** — the v0.2.30 lesson: the
   quality line and `.ocr/` kit exist *because* accuracy cannot be
   guaranteed; v0.4.1 inherits the honest-reporting posture, and the
   spec forbids turning the heuristic into a gate (it is reporting,
   ever).
3. **Sidecar adoption false positives** (a stray same-stem `.srt` from
   another cut) — mitigated by exact-stem-only matching + the adoption
   being named in report/plan/manifest; PAL/NTSC mismatched-timing
   sidecars are a documented limitation (B.6.3), not a solved problem.
4. **Two new external tools per platform widening the packaging
   surface** — Windows reuses b2m's vetted payload verbatim (with its
   post-build presence gates); Linux uses system tesseract with explicit
   resolution. No PATH guessing anywhere (the repo's standing
   discipline, run.py:17-21).
5. **Sequencing risk if v0.4.0 slips** — this design depends on the
   derived stamp (sub/idx conversion), the clock gate (timing
   invariant), and `record_step` (OCR observability). It must not land
   before v0.4.0 is validated; the doc is written to sit on those seams
   so the v0.4.1 lane is a pure addition afterward (per the directive's
   sequencing note).

**Bottom line:** VidLift today carries text subs only with an
all-or-nothing gate, silently drops every bitmap sub, and never sees
sidecars. v0.4.1 ports b2m's twice-field-proven unattended-OCR
machinery (seconv+Tesseract on Windows, direct-Tesseract on Linux,
honest fail-open everywhere, quality reporting + diagnosis retention as
first-class output), fixes the mixed-drop, adopts same-stem sidecars,
embeds mov_text + keeps the editable `.srt` per Eric's approved
defaults — and needs **zero re-timing machinery** because v0.4.0's
decode-truth clock gates already guarantee duration preservation. The
whole design is an additive v2 extension on v0.4.0's seams.
