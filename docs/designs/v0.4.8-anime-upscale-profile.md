# v0.4.8 — Anime Upscale Profile (binding design)

Status: binding 2026-10-26. Author: Bob (architect). Approved by Eric
2026-10-26 11:05 CDT. Implements the anime engine profile
(`realesr-animevideov3-x2`) for old-cartoon / DVD-era animation rips —
the seam deliberately deferred at v0.4.0 with the registry row sketched
in real-engine-adapter.md §3 (line ~77) and §9.5 (lines ~379-380) and
listed in sequencing-and-forge-brief.md (line 220) as "a one-row table
change plus its own validation." Forge implements against this document;
Karen validates against Section 10's test list. No code changes are part
of this design phase; this document plus measured artifacts are the
deliverable.

---

## 1. Why this milestone and why now

Eric has a batch of DVD-era cartoon rips to upscale. Real-ESRGAN's
general x2plus net (the v0.4.0 live-action profile) is the wrong tool
for flat-fill line-art sources: the RRDBNet's capacity is wasted on
large uniform regions, its texture synthesis invents false detail in
flat fills, and it rings on hard black outlines. The
`realesr-animevideov3-x2` net is a compact VGG-style model trained
specifically on anime video frames, dramatically faster on the same
hardware (the x2plus verification report measured ≈7.5-8x speedup vs
x2plus on llvmpipe: 5.0 s/frame vs 39.8 s/frame for a synth patch,
5.0 s/frame vs 41.8 s/frame for a real frame; the ratio tightens on
real GPUs but the order of magnitude holds), and demonstrably the
sibling project's "720p anime" answer (docs/designs/v0.4.4 §11 cites
the "Off/720p/720p anime" AI-upscale combo precedent).

The seam was built to admit this profile: `MODEL_TABLE` is the only
source of `-n`/`-s`, `verify_model_artifacts` keys on `spec.name`, the
GUI engine combo is already QSettings-persisted, and the MCP bridge
already accepts an engine selection per run. This design adds the
profile row and surfaces a per-run manual switch on all four of them
— no auto-detection, by deliberate house rule (see D3).

## 2. Measured artifacts (verified 2026-10-26)

Downloaded from the official Real-ESRGAN release assets. The binary
bundled with the Windows installer (`v0.2.0` zip, per
`.github/workflows/build-windows-installer.yml` lines 39-46) is
byte-identical to the binary in the older 20220424 zips (the x2plus
verification report confirms this: sha256 prefix `22c2296a…` for the

`07e49f7cbb4ede01ae4dd4c399d3a7e5846e3d2085c3128eff881e55cb7b1a0c` —
the verification report states hash parity across zips).

The v0.2.0 zips do NOT bundle model files — the workflow populates
`packaging/tools/realesrgan/models/` from `packaging/models/` at
build time (workflow lines 48-49), and `packaging/models/` currently
holds only `realesrgan-x2plus.{param,bin}` (vendored 2026-10-04 from
the conversion in `/home/yetisoldier/projects/x2plus-ncnn-verified/`).

The 20220424 zips DO bundle the stock models, including the anime one:

```
/tmp/realesrgan-20220424/models/realesr-animevideov3-x2.param   3,173 bytes
   sha256 b88ff4f00ebf019a7fdac17fdd45a7fd3665d37509efc5baf2e4da2e24420a04
/tmp/realesrgan-20220424/models/realesr-animevideov3-x2.bin     1,247,368 bytes
   sha256 548a36f9c3f4ab8da56cd3b13badf23968bee207b396dad14d04b830e5f2ab2d
```

Sizes are tiny next to x2plus (param 110,995 B; bin 33,434,888 B — the
anime profile's combined footprint is 1.25 MB, ~3.7% of the existing
lane). Installer bloat: +1.25 MB uncompressed, well under noise for a
600 MB-class installer (the bulk of which is FFmpeg, Tesseract, and
the engine binary). No ISS compression impact; `lzma2/max` already
handles the dominant artifacts.

### Engine-level verification of the native-2x claim

The x2plus verification report already established the engine binary's
behavior, and that report's own timing row (realesr-animevideov3 -s 2)
appears there. 2026-10-26 measurement against the actual released
binary confirms the net behaves as a true native-2x model:

- 64x64 probe at `-s 2` → exactly 128x128 (`-n
  realesr-animevideov3-x2` and `-n realesr-animevideov3` are
  byte-identical: sha256 `e5eadda1…` for both outputs).
- 65x47 odd-size probe at `-s 2` → exactly 130x94 — the correct 2x
  rule, matching the x2plus verification standard (640x360 → exactly
  1280x720; 639x359 → 1278x718 in the sibling report).

The param file's `Interp Resize_37 … 1=4.000000e+00 / 2=4.000000e+00`
followed by `Interp Resize_40 … 1=5.000000e-01 / 2=5.000000e-01` is
the animevideov3 architecture's fixed internal 4x-then-half-scale
combination, always exposed to the engine as a scale-2 output. Unlike
the v0.2.25 corruption case (x4plus native-4x net misused at `-s 2`),
`-n realesr-animevideov3-x2 -s 2` IS the native mode — `-s 2` here is
the documented pairing the engine's own help text names as the default
model-and-scale combination. Verified live on the actual released
binary; no conversion or fold is needed (no `Reorg` layer appears in
this param; the v0.2.0 binary accepts it as-is, and the run produced
sane image content, not garbage).

## 3. Decisions

### D1 — Vendor the model artifacts into `packaging/models/`, hash-pin identically to x2plus

Add two files to the repo at `packaging/models/realesr-animevideov3-x2.param`
and `packaging/models/realesr-animevideov3-x2.bin` with the exact bytes
measured above (3,173 B / 1,247,368 B, hashes above). Rationale:

- Matches the existing `packaging/models/realesrgan-x2plus.*` lane
  verbatim — same provenance rule (vendored bytes, verified at build
  time and at first use), same on-disk layout
  (`packaging/tools/realesrgan/models/` at install time, models/
  beside the engine binary).
- The runtime resolution (`resolve_realesrgan_models` in
  `vidlift/tools_realesrgan.py` lines 116-144) already supports the
  bundled `models/` directory; nothing else discovers models.
- The alternative — runtime download — reintroduces a class of
  failure mode the x2plus lane eliminated in v0.4.0 (network at first
  use, no hash pinning at build, no offline installer guarantee).
  Rejected.

Build-time hash verification (`.github/workflows/build-windows-installer.yml`,
lines ~50-51): extend the existing pwsh block to assert the anime
pair's sha256 alongside x2plus, so a substituted model never ships.
The installed-artifact validation block (lines ~132-134) similarly
asserts both files land under
`$install\tools\realesrgan\models\realesr-animevideov3-x2.{param,bin}`.

Runtime hash verification: extend
`vidlift/tools_realesrgan.py::MODEL_ARTIFACTS` with a second entry keyed
on `"realesr-animevideov3-x2"` carrying the (size, sha256) pairs above.
`verify_model_artifacts` (lines 147-198) runs per model name; the
`_HASH_CACHE` key already includes the model name, so the two profiles
verify independently on first use per process.

### D2 — Registry row: `"anime" → ModelSpec(name="realesr-animevideov3-x2", native_scale=2)`

One line in `vidlift/engine_ncnn.py::MODEL_TABLE` (currently lines
424-433):

```python
MODEL_TABLE: dict[str, ModelSpec] = {
    "live-action": ModelSpec(name="realesrgan-x2plus", native_scale=2),
    "anime": ModelSpec(name="realesr-animevideov3-x2", native_scale=2),
}
```

This is the exact row sketched in real-engine-adapter.md §3 line 77,
with the comment above the table (lines 424-429) extended to record
the 2026-10-26 verification (the Section-2 measurements here).

`ModelSpec.native_scale=2` is verified above, not assumed. The b4 test
pattern (no constructed engine command line may pair `-s` with a value
other than the selected model's `native_scale`) automatically extends
to both rows once the table has them — no per-profile logic anywhere.

The `-n`/`-s` plumbing passes through the engine command line untouched
(engine_ncnn.py §1770-1772 — `-m`, `-n`, `-f` plus `-s` at line 1769
built once per chunk). `select_engine` (lines 948-994) currently
hardcodes `MODEL_TABLE["live-action"]` at lines 977 and 986; that is
the seam point where the profile name must ride through (see D4).

### D3 — Profile selection is manual-only, no auto-detect, default `"live-action"`

Three reasons, all house rules:

1. **Honesty surface.** Auto-detection implies a classifier, and a
   classifier that flips a user's run to "anime" on a false positive
   produces exactly the wrong ringed-flat-fill output D1's rationale
   warns about. Manual opt-in means every anime run is the user's
   stated intent, matching how the GUI engine combo ("Auto / ncnn /
   Stub") is a user choice with a recorded `engine_note`.
2. **Sibling precedent.** The sibling's UX was "Off / 720p / 720p
   anime" — per-file manual selection, no auto-detect. The UX
   contract this design inherits.
3. **Implementation risk.** The classification surface
   (`vidlift/classify_sample.py`) is about interlace, not content
   type. Adding a second classifier path for v0.4.8 violates the
   "one concern per milestone" convention (v0.4.5 progress honesty
   was a similar surgical slice).

Default: `"live-action"` (the only profile v0.4.7 and earlier
shipped; existing user runs and cached ETAs stay valid-by-default).

### D4 — Profile plumb-through: `profile` keyword on `run_file` and `select_engine`, plus a kwarg to `NcnnVulkanEngine`

The `NcnnVulkanEngine` adapter (engine_ncnn.py line 1009) already
accepts `profile: str = "live-action"` and looks up
`MODEL_TABLE[profile]` at line 1028. The seam is already profile-
aware; the wiring just never carries a profile in.

`select_engine` (line 948) must gain a `profile: str = "live-action"`
keyword (placed before `binary` to match the keyword-arg convention
there) and pass it into both hash verification (lines 977, 986 —
swapping the hardcoded `MODEL_TABLE["live-action"]` for
`MODEL_TABLE[profile]`) and the `NcnnVulkanEngine(...)` constructor
call. Failure mode: an unknown profile raises `UpscaleError` naming
the profile (matches the existing `unknown engine request` failure at
line 995).

`run_file` (vidlift/run.py line 1108) gains a corresponding
`profile: str = "live-action"` keyword, threaded through to
`select_engine(profile=profile, ...)` at the line where
`engine_request` is resolved. When `engine=` is passed explicitly
(tests / bridge seam), the caller-built engine carries its own
profile; `profile` is ignored on that path (the explicit engine seam
wins, same discipline as `engine_request` being ignored when `engine`
is passed).

`gpu_probe_frame` (line 839) already takes `spec: ModelSpec | None`
keyword (line ~844): `select_engine`'s auto path passes
`spec=MODEL_TABLE[profile]` so the probe actually exercises the
profile's model, not always the live-action one. The per-process
`_PROBE_CACHE` key (line 715, `(binary, models_dir)`) must extend to
include `spec.name`: a probe pass on one profile must not silently
bless another (the current cache keying is fine for v0.4.7 where only
one model exists; with two models the key must discriminate). This is
the only structural change to the probe beyond passing `spec=`.

### D5 — Surface deltas (four surfaces, all manual, all persist)

**Python API.** `run_file(..., profile: str = "live-action")`. The
docstring's v0.4.7 section gains one sentence; no other semantics
change. The keyword is additive at the end of the signature (the
existing `subtitle_ocr: bool = True, replace_source: bool = False`
pattern).

**CLI.** Add `--upscale-profile {live-action,anime}` to
`vidlift run` (cli.py, after the `--engine` block at lines ~468-475).
Long name over short forms, justified:

- The flag names a *selection of model weights*, not an engine. A
  short flag (e.g. `--profile`) would collide with
  `cProfile`/`profile` semantics users reach for; a single letter
  (`-p`) is taken by common conventions (`--preset`, `--profile`,
  `--plan` in other tools).
- The flag must be self-documenting in scripts and `.bat` files
  (the Eric use case).
- Sibling precedent: the sibling used `--mode live-action|anime`
  internally; "upscale-profile" is the analogous unambiguous English
  name for *which upscale model family*.

The parser help text states: `default "live-action"; choose "anime"
for cel-animation / flat-fill sources (DVD cartoons, anime), where the
animevideov3-x2 model is faster and avoids false texture in fills.
Manual switch only — VidLift does not auto-detect content type.`
Threaded through `_cmd_run(..., upscale_profile=...)` to
`run_file(profile=...)`.

**GUI.** Add a `QComboBox` named `profile_combo` to the existing
control strip, populated with the display labels and `data=` keys
mapping to the registry names (the `ENGINE_CHOICES` pattern at
gui.py lines 106-110):

```python
PROFILE_CHOICES: list[tuple[str, str]] = [
    ("Live action (general x2plus)", "live-action"),
    ("Anime / cartoons (animevideov3-x2)", "anime"),
]
```

Grid position — **row 1, columns 2-3** (`grid.addWidget(QLabel("Model
profile"), 1, 2)` and `grid.addWidget(self.profile_combo, 1, 3)`),
learning from the v0.4.7 D2 collision (changelog entry: "the checkbox
spanned grid columns 5-7 and clipped under cancel_button at (1, 7);
it now spans columns 5-6"):

- Row 0 columns 0-8 are fully occupied (Add / Add Folder / Clear /
  GB-hour / Output Folder / Plan / Start).
- Row 1 columns 0-1: engine label + combo (existing).
- Row 1 columns 2-4: subtitle_ocr `QCheckBox` (existing, span 3 at
  line 618).
- Row 1 columns 5-7 are spoken for: replace_source (1, 5, 1, 2 →
  spans 5-6) and cancel_button (1, 7).
- The only free cells on row 1 are therefore nonexistent — the
  profile combo cannot fit there.
- Row 2 currently has `monitor_check` at (2, 0, 1, 7) — a span
  covering columns 0 through 6.

**Resolution:** move `monitor_check` to span (2, 0, 1, 5) — columns
0-4 — and place the new profile combo at row 2, columns 5-6:
`grid.addWidget(QLabel("Upscale profile"), 2, 5)` and
`grid.addWidget(self.profile_combo, 2, 6)`. This mirrors the
replace_source 2-column span on row 1 (a wide label + control pair
sitting over two grid columns) and keeps `cancel_button` untouched at
(1, 7). The v0.4.7 geometry test
(`test_v047_replace_checkbox_no_overlap_with_cancel`) needs a sister
assertion against the new profile_combo's rect vs cancel_button.

Tooltip (honest, in the same voice as `engine_combo`'s at line 380):
`"Live action uses the general Real-ESRGAN x2plus net (default).
Anime/cartoons uses the animevideov3-x2 net — faster on flat fills
and line art. Manual switch; VidLift does not auto-detect content
type. Persists across sessions."`

QSettings persistence: key `"upscale_profile"` under
`QSettings("YetiWurks", "VidLift")` (matching the `"engine"` key at
gui.py line 429 and the `"replace_source"` key at line 366). Load on
init (mirroring `_load_engine_choice` at lines 426-432), persist on
change (mirroring `_engine_changed` at lines 547-551).

The combo is disabled while a batch is running (the engine_combo
disables at line 933; profile_combo follows the same rule and tooltip
at line 934).

`start_upscale` (line 902) passes the profile through the bridge:
`options["upscale_profile"] = self.profile_choice`, which the bridge
maps into the run job's options → `run_file(profile=...)`.

**MCP bridge.** Add the field to `schemas.py::_OPTIONS_RUN` (line 41):
`"upscale_profile": {"type": "string"}` — string not enum, matching
`"target"`'s permissive shape; validation of the value happens in
`run_file`'s `select_engine` path (an unknown name raises
`UpscaleError`, which the bridge already converts to a job failure
with `error=` named — same shape as an unknown `engine` value landing
in `select_engine`'s final raise at line 995). The absent-defaults
rule: when `upscale_profile` is not present in options, `run_file`'s
`profile` kwarg defaults to `"live-action"` and behavior is identical
to v0.4.7.

`jobs.py::_execute_run_job` (line 116) gains one line in the
`run_file(...)` call: `profile=options.get("upscale_profile",
"live-action")` beside the existing `engine_request=options.get(
"engine", "auto")` line (currently ~196-198). `client_local.py`'s
`enqueue_run` (line 100) needs no change — the GUI passes
`options["upscale_profile"]` already and the options dict is passed
through as-is (`opts = dict(options or {})`).

The bridge's tools/list surface (server.py's schemas) is rebuilt from
`TOOL_SCHEMAS`, so the new field appears in `tools/list` automatically
— no separate schema publish step, no protocol revision (the schema
validator's unknown-field-reject rule means older clients sending no
`upscale_profile` are accepted, and newer clients sending the field
are accepted once the bridge supports it — the schema registry is the
same shape rule as v0.4.7's `replace_source` addition at line 48).

### D6 — Plan expectations stay honest; one additive note for anime sources

`vidlift/plan.py::_expectation` (lines 152-164) keys on
`report.source_class`. SD DVD rips of cartoons hit the existing
`SOURCE_DVD_MPEG2_RIP` branch — `"best 720p that source can give;
good, not transformative"` — which remains true: the anime net makes
flat fills *smoother and cleaner*, not more detailed (it cannot
invent detail the source lacks). For animation specifically the
"good, not transformative" wording actually undersells slightly: line
art stays crisp and mosquito noise around outlines shrinks visibly.
The honest phrasing stays — undershoot, never oversell.

One additive sentence appended only when (a) the source class is
`SOURCE_DVD_MPEG2_RIP` AND (b) the run-time profile is `"anime"`,
worded:

> "Anime upscaling model: strong fit for flat fills and line art
> (common in cel animation); not for live-action content."

Implementation seam: `build_file_plan` does not currently know about
the profile — the plan is content-agnostic by design (the profile is
a *run* knob, not a *plan* knob; the sibling UX made the profile a
per-run choice at the GUI/CLI level, not a plan-time probe). Rather
than contaminating plan.py with profile awareness, the additive
sentence appears at the *report* surfaces that already have the
profile in scope: the CLI's run-report (cli.py) and the GUI's
detail-text render (gui.py's `detail_text`). When `profile ==
"anime"`, the expectation bullet appends that sentence; otherwise
it's omitted. This keeps `PlannedFile.expectation` stable and lets
plan-level consumers (MCP `plan` tool) stay untouched — the bridge's
`plan` payload (mcp_bridge/tools.py::_plan_payload) does not take a
profile at all, only `run` does.

### D7 — The `native_scale` check pattern extends unchanged; one new b4-style assertion

The b4 pattern (`-s` always equals `native_scale`, x4plus can never
be constructed) is per-row. Adding a second row automatically extends
the guarantee to both rows. One new test is needed:
`test_b4_anime_profile_scale_pairing` — for both rows, every
constructed engine command line's `-s` argument equals
`MODEL_TABLE[profile].native_scale`. Additionally, an unknown-
profile constructor call must raise `UpscaleError` naming the
profile (engine_ncnn.py line 1029-1030 already covers this).

### D8 — gate_tolerance / probe-frame need no per-profile change

`gate_tolerance` (engine_ncnn.py lines 435-437) is `max(0.5 s,
0.01%)` over a duration — content-agnostic by construction. The b3
matrix survives unchanged.

The GPU probe frame (lines 839-945) currently runs one 64x64 PNG
through the model and asserts the output geometry is exactly
native_scale × input. With `spec=MODEL_TABLE[profile]` carried in
(see D4), the probe exercises the *correct* model — a 64x64 probe
under the anime profile produces a 128x128 output exactly as the
live-action one does. The verification contract is unchanged: engine
binary decodes PNG → runs the named model with the named scale →
output geometry matches the spec. Nothing in the probe body varies
per profile.

### D9 — The v0.4.7 cleanup contract needs no per-profile change, but the anime profile sweeps identically

The success-cleanup contract (`run.py::_SUCCESS_SCRATCH_EXTENSIONS`,
lines 928-945) removes `<run-id>.prepared.mkv`, `<run-id>.prepared.
upscaled.mkv`, `<run-id>.engine-work/`, `<run-id>.ocr-work/` — all
run-id namespaced. The mezzanine path is profile-agnostic
(`Path(prepared_path).with_suffix(".upscaled.mkv")` at engine_ncnn.py
line 1188 is the same for both profiles — the model name does not
appear in the path). The B.5 rejected-mezzanine rename (engine_ncnn.py
lines 1457-1459) is likewise profile-agnostic.

The Karen r2 D3 rule — a successful run sweeps the mezzanine, a
failed one retains it — holds byte-for-byte under the anime profile:
same extensions, same paths, same exact-name discipline. A new test
(`test_anime_profile_success_deletes_engine_mezzanine`) runs a stub-
driven anime-profile run end-to-end and asserts the success sweep
fires, mirroring `test_success_deletes_engine_mezzanine_karen_r2_d3`
exactly. Likewise `test_anime_profile_failed_run_retains_engine_
mezzanine` mirrors the failure side. No cleanup code change is
required; the tests pin the profile-agnostic claim.

### D10 — Observability Heartbeat is untouched

`run.py::run_with_heartbeat` (lines 285-341), the `_SUCCESS_SCRATCH_

- **b22 (plan expectations):** `_expectation` returns the unchanged

### Karen's gate run (real content)

The Karen gate replays the v0.4.7 shape: a real short clip through
the real engine on the real binary, asserting exit, output geometry,
manifest honesty, cleanup, and a frame-eyeball. For the anime
profile the gate needs **genuinely cel-animation content** — NOT
Eric's rips (CI fixtures cannot be derived from licensed DVD rips).

Source: **a public-domain cel-animation short.** Candidate: a
Fleischer Studios cartoon whose copyright has lapsed into the public
domain — e.g., *Superman* (1941, "The Mad Scientist" / "Billion
Dollar Limited" etc., entered PD in the US through non-renewal, hosted
on archive.org), or *Popeye* shorts from the 1930s in PD, or *Betty
Boop* shorts with lapsed copyright. The gate fixture is derived:

- Source spec: SD resolution (~320x240 or ~480x360 after prepare),
  duration ~2-5 seconds, content dominated by flat fills + black
  line art (the failure mode x2plus invents texture into).
- Extraction: `ffmpeg -ss <t> -t 4 -i <pd-source>.mp4 -c:v mpeg2video
  -q:v 6 -c:a mp3 fixture-cartoon.vob` — a DVD-class MPEG-2 in VOB so
  it exercises the SOURCE_DVD_MPEG2_RIP path end-to-end, matching
  Eric's real use.
- Storage: checked into `tests/fixtures/media/` (new directory; the
  existing `samples/` is empty and not a fixtures location). The clip
  is ~1 MB at MPEG-2 quality 6 for 4 s — well under any git-lfs
  threshold. License note file beside it citing the PD status and the
  archive.org URL it was pulled from.
- The Karen gate runs this once per profile — anime profile expected
  to complete cleanly and produce a smoother result than live-action
  profile on the same clip (the D1 rationale), but the *gate* is the
  mechanics: output verified at 720p HEVC, manifest records the
  selected profile, cleanup sweeps, no false "simulated" claim. The
  frame-eyeball comparison (anime vs live-action on the same source)
  is a Karen-attached artifact, not a hard assertion (visual quality
  is the Eric hand-off, u-pattern).

If none of the named PD candidates survive a license re-check at
implementation time, the fallback is a CC0 cel-animation short from
Blender Foundation's open movie catalog (e.g., *Big Buck Bunny* has
cel-adjacent flat-shaded sequences at SD resolutions after a downscale
to DVD geometry) — but the named Fleischer path is preferred because
it is the exact content class Eric's rips live in.

## 7. What this design does NOT do (explicit non-goals)

- No auto-detection of animation content (per D3).
- No third profile (no x4 lane; no animevideov3-x3/-x4 wiring).
  The MODEL_TABLE extension rule from v0.4.0 holds: profiles are
  added at native_scale and only when verified against the actual
  binary.
- No changes to `probe.py`, `plan.py`'s core math, `benchmark.py`,
  or the subtitle pipeline. The benchmark cache keys
  `(engine, model, geometry bucket)` already include the model name
  — anime-profile benchmarks land in their own bucket automatically,
  and a live-action cached constant is not claimed for anime runs.
- No retry-with-backoff, no watch folders, no 1080p, all per the
  v0.4.0 deferred list.
