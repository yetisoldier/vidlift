# VidLift v0.4.5 — Progress Honesty (Log-Tail Pinning, Stage Labels, Registry Reload, D1 Lane)

Status: binding design 2026-10-20. Author: Bob (architect subagent). Consumers: Forge (implementation), Karen (validation). Trigger: Eric's live v0.4.4 run today — the packaged Windows GUI gave *no visible sign of activity* during a 23+ minute silent phase: the log widget never scrolled, the only progress surface was "estimating …", and the SD prepared-count probe emits no frame progress for its whole duration (design B.6's step heartbeat touches `last_activity_at` but writes *no log line*, so a log-tail watcher sees silence).

Scope gate: handoff doc, no production code. Forge implements the slices in §9; Karen enforces §8.

## 2. Fix 1 — Tail-pinning log widget (D-tail)

**Where:** `vidlift/gui.py` only. No bridge/runner changes required — the snapshot already carries the full tail.

**Contract** (ported discipline from the sibling's log_panel rules; named here as the v0.4.5 rule):

1. **Pin to tail by default.** Every re-render of `run_log_tail` ends with the scrollbar at maximum (bottom).
2. **Scroll-up override.** If the user scrolls up *even one line* before a tick lands, the next re-render does **not** yank them back down — the widget enters "user-inspecting" mode and stays where the user put it.
3. **Return-to-tail affordance.** The moment the user scrolls back to the bottom (within a small pixel tolerance, e.g. ≤8 px from `maximum`), pin-to-tail re-engages on the next tick.
4. **Reset on job change.** When the *job set* rendered changes (new `job_ids[0]`, terminal transition, batch start), the widget force-pins to tail once — user override applies only within one continuous job view.
5. **No content churn.** The existing `_set_text` setText-only-on-change rule extends to the log: if the tail text is byte-identical to what's rendered, do not touch the document at all (this also avoids scrollbar-jitter on the 1 Hz tick).

**Mechanism sketch (handoff shape, not code):**

- Subclass-free approach: keep `QPlainTextEdit`, add two helpers on `MainWindow`:
  - `_render_log_tail(text: str) -> None` — replaces `_set_text_log`. Compares against current content; on change, captures `was_pinned = self._log_tail_user_at_bottom()`, calls `setPlainText`, then if `was_pinned or self._log_force_pin_next` calls `scrollbar.setValue(scrollbar.maximum())`.
  - `_log_tail_user_at_bottom() -> bool` — reads `verticalScrollBar().value() >= maximum() - _LOG_PIN_TOLERANCE_PX`.
- Connect the scrollbar's `valueChanged` to clear/set a `_log_user_scrolled_up` flag, and `rangeChanged` to track the maximum (Qt's range changes on every `setPlainText`).
- Constant: `_LOG_PIN_TOLERANCE_PX = 8` — module-level, tests shrink it.

**Qt subtlety Forge must respect:** on `setPlainText` the document is *replaced*, so `rangeChanged` fires synchronously *before* `valueChanged` settles. Read "was at bottom" **before** calling `setPlainText`, never after.

**Out of scope:** incremental append-only rendering, search, copy button. The widget stays read-only `setPlainText` on the 1 Hz tick.

## 3. Fix 2 — Count-pass & stage honesty (D-count + D-eta)

Three coordinated sub-fixes, ordered cheapest-first. None lie: every visible number is either measured or labeled as its honest kind.

### 3a. Engine emits a liveness *log line* during the count pass (D-count primary fix)

**Where:** `vidlift/engine_ncnn.py::_probe_frame_count_alive`.

Today it calls `self._step(label)` every `PROBE_HEARTBEAT_SECONDS` (5 s) but writes no log line. Add a throttled `self._log(...)` call alongside the step touch, cadence `PROBE_HEARTBEAT_LOG_SECONDS = 30.0` (same shape as `run.py::HEARTBEAT_LOG_SECONDS`):

```
<label>: heartbeat t=<n>s (decode-count pass; no per-frame signal until ffprobe summary)
```

The `<n>` comes from a captured `started = time.time()` before the thread launches. The line is honest — it names the phase, names the elapsed wall time, and tells the user *why* there is no frame counter (the count is the denominator being measured; it cannot be its own numerator).

**Why not parse ffprobe stdout for progress?** `-count_frames` does not emit per-frame progress on any stream in any ffmpeg release we target; the only signal arrives in the final summary block. Pretending otherwise would be inventing data. The honest signal is wall-clock + the label.

### 3b. Stage-label discriminator + sub-progress once the count lands (D-eta partial fix)

**Where:** `vidlift/gui.py::run_stage_label` and `vidlift/gui.py::_consume_running_snapshot`; small additive field in `run.py::RunState.progress` (schema-v2 additive convention, same as v0.4.1's `subtitles` block).

The runner already records `progress["step"] = "prepared-count-probe"`. Add one more additive key written by the same seam:

- `progress["phase_note"]` — a short human-readable string the engine sets when entering a sub-stage that has no measurable denominator. The engine writes it at the same moment it writes `step`, e.g.:
  - `"counting frames (no per-frame signal until done)"` for the decode-count pass,
  - `"upscaling chunk {n}/{N}"` from the existing chunk loop (already known, just not currently recorded),
  - `"extracting chunk {n}/{N}"`, `"reassembly"` — all existing labels in `engine_ncnn.py`'s chunk flow, promoted to the runner state via the `on_step` seam.

`run_stage_label` changes:

| `current_phase` | `progress["step"]` | Rendered label |
|---|---|---|
| `upscale` | `prepared-count-probe` | `upscaling — counting frames (this can take 10–40 min on SD sources; no per-frame ETA exists yet)` |
| `upscale` | `chunk` (and `chunk_index`, `chunk_total` known — see below) | `upscaling chunk 3/12` |
| `encode` | `encode` | `encoding (heartbeat t=<n>s)` |
| `verify` | `verify` | `verify — full decode (heartbeat t=<n>s)` |

The engine's chunk loop also raises two *existing* counters through `on_progress` (`frames_done`, `frames_total`) once the prepared-count probe lands; those already flow into `stage_bar.set_value`. No change there — that's the denominator arriving exactly when honest measurement starts.

`gui.py::_consume_running_snapshot` adds one clause: when `progress.get("phase_note")` exists, show it as the parenthetical suffix of the stage label and route it through `_set_text` (no repaint churn on identical values).

### 3c. ETA "first measured throughput" surfacing (D-eta finish)

**Where:** `vidlift/mcp_bridge/tools.py::_eta_seconds` and `vidlift/gui.py::_consume_running_snapshot`.

Current `_eta_seconds` requires a benchmark constant AND `frames_total > 0` — both fine, but the GUI's *display* rule is the stricter problem: when `eta_seconds` is None, the bar stays in busy mode with "estimating …" forever. v0.4.5 keeps the never-lie rule but adds two honest display states:

1. **"Measuring…" state** — shown while `current_phase == "upscale"` AND `frames_total == 0` (i.e., count pass still running). Label: `"measuring — counting frames…"`. This is *honest* because it names what the pipeline is doing to get an ETA.
2. **ETA the moment throughput exists** — when `frames_total > 0` and `frames_done >= 1` and we have the bridge's benchmark constant, `_eta_seconds` already returns a number; the bar drops busy on the same tick. No change to the math; the fix is that the stage label now *predicts* when this will happen ("as soon as the first chunk completes").

**Explicit anti-lie rule (binding):** a benchmark *stub* constant never feeds the GUI's numeric ETA (already enforced in `_benchmark_eta_for_job`). A benchmark *ncnn* constant on a *ncnn* job is honest. No new ETA sources in v0.4.5. No fabricated percentages.

## 4. Fix 3 — Registry mtime-based reload (D2)

**Where:** `vidlift/mcp_bridge/registry.py` only.

**Mechanism:**

- `Registry.__init__` records `self._loaded_mtime = self._stat_mtime_or_none()`.
- Every *read* entry point (`get`, `require`, `queued`, `running`, `history`, `queue_position`, `get_cancel_flag` is exempt — it's in-memory) begins with `self._maybe_reload()`.
- `_maybe_reload()`:
  1. Stat the file. If `mtime == self._loaded_mtime`, return — the common case is one `stat` per call.
  2. If mtime differs, take `self._lock`, re-stat inside the lock (another writer may have reloaded us already), and if still different, re-parse the JSON and **merge** by `job_id`:
     - Rows in the file win over in-memory rows for all *persisted* fields.
     - In-memory `_live` dicts and `_cancel_flags` survive (they are process-local by design).
     - A job present in memory but absent in the file is **left alone** (this-server-owned in-flight job, not yet flushed — the `save()` that created it is what put it in the file in the first place; absence means another writer *deleted* it, which the current writer set never does. Defensive: log a warning when this happens).
  3. Update `self._loaded_mtime` to the new value.
- `save()` updates `self._loaded_mtime` from the post-write stat, so a save→read sequence doesn't trigger an unnecessary reload.

**Failure semantics:** a failed stat or parse in `_maybe_reload` is **soft** — log via `services.log_event` if available, keep the in-memory view. The load-fail hard-raise stays at startup (`load()`), where it belongs.

**Explicit non-goal (documented for Karen):** the registry remains a single-writer story in any one process. mtime reload exists so that *separate* processes (a long-running MCP server, a GUI that starts after enqueue) converge on the same truth. It is **not** a multi-writer concurrency story — the enqueue path already takes `self._lock` and calls `save()`, which is sufficient for the single-writer-multiple-reader topology VidLift actually has.

**Test seam:** `_maybe_reload` is a method so tests can monkeypatch `_stat_mtime_or_none` to simulate mtime changes without touching the filesystem.

## 5. Cross-cutting: a heartbeat surface rule (the "23-minute silence" guard)

The deepest lesson from today's live observation: **no phase of the pipeline may run for more than N seconds without emitting at least one observable signal** (log line, step label change, or progress counter update). v0.4.5 elevates this to a repo-wide expectation:

- `HEARTBEAT_LOG_SECONDS` (currently 30.0 in `run.py`) becomes the named ceiling. Any seam that runs longer than 30 s without an external-command heartbeat MUST write a log line or update a progress field. v0.4.5 fixes the count-probe violator (§3a). Forge does not hunt down other violators in this milestone — the rule is forward-looking.

This is one paragraph in `docs/development.md` (a new "Observability heartbeat rule" subsection) — Forge adds it in the same PR. No code enforcement tool this milestone; the rule's teeth are Karen's tests.

## 6. Fix 4 — D1: registry lane decision (Eric's call, NOT made here)

The Windows GUI writes to `%LOCALAPPDATA%\YetiWurks\VidLift\jobs.json`. The minipc MCP wrapper reads `/home/yetisoldier/.vidlift/jobs.json`. Two physically separate registries. Three options:

| Lane | Mechanism | Pros | Cons | Risks |
|---|---|---|---|---|
| **(a) Windows-side MCP entry** | Install the `vidlift` Python package on the Windows host; run `vidlift mcp-server` there; the gateway-side wrapper becomes a thin stdio proxy (ssh-winrm equivalent) OR Eric uses the Windows-side MCP directly via the OpenClaw-connected Windows node. | One registry, one writer (the Windows host owns it). No sync semantics. Honest by construction. | Requires `vidlift-mcp` install + dependency solve on Windows. Two MCP endpoints (dev/minipc + prod/Windows) instead of one. | OpenClaw-side plumbing; depends on the Windows node-host state (currently pending). |
| **(b) Read-only sync lane** | A small one-way mirror: a cron/systemd timer on minipc tails the Windows registry via SSH, writes to `~/.vidlift/jobs.json.readonly`, and the MCP `list` tool gains a separate "remote (read-only mirror)" view. Writes still go to one side only. | minipc MCP retains full visibility over Windows-side jobs. No shared-write semantics. | Two physical files, delayed truth. The dishonest-queue risk Eric named today: an MCP-side `enqueue` against the *mirror* would silently diverge. Mitigation: the mirror directory is owned by a different filename (`jobs.json.readonly`) and the `enqueue` tool refuses to target it (explicit one-way semantics). | Stale-mirror reads lead to bad cancel/status decisions if the user confuses the views. Naming must make mirror-ness unmistakable. |
| **(c) Document the split, defer unification** | v0.4.5 docs update only: `docs/architecture.md` gains a "State location" subsection stating the split, when each lane is the truth, and the rule "enqueue and observe on the same host". | Zero code. Honest documentation. Defers the plumbing risk to when Eric actually wants cross-machine MCP. | Today's defect (MCP can't see GUI jobs) remains. | Eric's stated workflow (kick off via GUI on Windows, sometimes query from MCP on minipc) stays partially broken. |

**Architect recommendation:** (c) for v0.4.5 with a hard commitment that v0.5.0 picks (a) or (b). Rationale — today's fire is *progress honesty*, not cross-machine visibility; (a) requires a Windows-side install decision that deserves its own design; (b)'s one-way mirror is engineering against a problem whose frequency Eric hasn't yet stated. Documenting the split in v0.4.5 costs one docs paragraph and unblocks "I know I'm not supposed to enqueue from minipc against the Windows GUI" today.

**But the call is Eric's.** The dishonest-queue risk he flagged this morning rules out naive bidirectional sync; both (a) and (b) preserve a single-writer invariant. If Eric says "do (a) now," the v0.4.5 doc gets an amendment and the slice list grows; the implementation cost is bounded (one OpenClaw MCP wrapper change + install docs).

## 9. v0.4.5 scope vs. defer-later

**Ship in v0.4.5 (same-day):**

- **Slice 1** — Fix 1 (tail-pinning). Smallest, highest-visibility, fully in one file. Tests 1–6.
- **Slice 2** — Fix 2 (§3a + §3b + §3c). The liveness log line alone would have changed today's run from "looks frozen" to "clearly alive". Tests 7–13.
- **Slice 3** — Fix 3 (registry mtime reload). Independent of Slices 1–2; lands in parallel if Forge has bandwidth, otherwise ships after. Tests 14–19.
- **Slice 4** — D1 documentation-only (lane (c)) **unless Eric chooses (a) or (b) by design review**. Plus the §5 heartbeat rule paragraph in `docs/development.md`.

Each slice is independently revertable. None blocks another's merge. Recommended merge order: 1, 2, 3, 4 — but any order works.

**Defer to v0.4.6+:**

- Cross-machine registry unification (D1 lanes (a)/(b) plumbing).
- Append-only incremental log rendering (current `setPlainText` on a 40-line tail is plenty fast).
- Search/copy in the log widget.
- Repo-wide enforcement of the §5 heartbeat rule (a linter that walks for seams with no log/step emission — interesting but not same-day).
- Per-phase wall-time histogram in the GUI ("your last 3 count passes took 12–18 min") — nice-to-have, requires persistence.

**Out of scope for the v0.4.x line entirely:**

- Multi-writer registry semantics.
- Web-based GUI.
