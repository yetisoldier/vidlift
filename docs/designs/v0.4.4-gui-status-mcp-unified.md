## 3. Data/control flow and public contracts

The flow is straight-line; the GUI never bypasses the bridge:

```
GUI MainWindow
  │
  ├─ Add Files → self.files                       (in-memory list only)
  ├─ Plan Batch → probe_and_classify + build_batch_plan
  │                  (read-only; same code path as tool_plan)
  │
  └─ Start Upscale
        │
        ▼
  mcp_bridge.client_local.enqueue_run(paths, options, engine, cb)
        │
        ▼
  Registry.enqueue(kind="run", ...)  →  JobExecutor.notify_new_work()
        │
        ▼ (worker thread, exactly as today)
  jobs._execute_run_job → run_file(...,
                                  engine_request=options["engine"],
                                  state_box=state_box,
                                  cancel=CancelFlag)
        │
        ▼ (per-second signals into the GUI thread)
  GUI polls client_local.status_snapshot(job_id) once a second
        │
        ▼
  Registry read + RunState.to_dict() (live)  →  Run panel update
  Cancel button → Registry.cancel(job_id)  (one path, MCP-side too)
```

Public contracts (additive; nothing in `mcp-bridge.md` is contradicted):

- `client_local.enqueue_run(paths, options, engine) -> list[str job_ids]`. Validates paths exist; refuses more than `MAX_GUI_BATCH = 64` files per click with a `QMessageBox`. Returns the IDs in submission order so the Run panel rows map 1:1.
- `client_local.status_snapshot(job_id) -> dict` — exactly the bridge `_status_payload` output, minus the stdio envelope. The GUI's per-second tick is a read-only client of the same `_status_payload` code path; no fork.
- `client_local.cancel(job_id) -> str` — same string values as `tool_cancel`'s second return: `cancelling | cancelled | not-found | already-finished`. The GUI does not own its own cancel flag.
- `client_local.history(limit=20) -> list[dict]` — read-through to `Registry.history()`; same shape as `tool_list`'s `history` block.
- Engine choice flow: `options["engine"]` ∈ `{"auto","stub","ncnn"}`. It rides the registry JobRecord's `options` dict, so live-status consumers can read back what the user picked; on job claim `_execute_run_job` passes it as `engine_request=options["engine"]`. **No GUI-side engine resolution**, ever — selection stays inside `run_file` so honesty rules (probe-frame fallback, MissingToolError, fail-open) stay centralized.

The GUI's old `UpscaleWorker` (in-thread serial loop) is **retired**. There is exactly one worker (the bridge's `JobExecutor`) and the GUI becomes a view. Cancellation, restart sweep, manifest persistence, and history all come for free.

## 5. MCP / job-registry unification design

The registry and executor are already correct; what's missing is a consumer that isn't the MCP stdio server.

**Server refactor (additive)** — `vidlift/mcp_bridge/server.py` grows:

```python
def build_services(state_dir: Path | None = None) -> BridgeServices: ...
```

which extracts the existing registry/executor construction from `main()` without changing any tool behavior. `main()` calls it. The GUI also calls it. Same objects in both worlds.

**In-process client** — `vidlift/mcp_bridge/client_local.py`:

- `enqueue_run(paths, options, engine)` → wraps `Registry.enqueue` and `JobExecutor.notify_new_work`. Validates paths, sets `options["engine"]`, returns `job_id`s in submission order.
- `status_snapshot(job_id)` → returns `_status_payload(services, registry.require(job_id))`. Imports the bridge's `_status_payload` directly from `tools.py` (no fork).
- `cancel(job_id)` → delegates to `services.registry.cancel(job_id)`. Never sets its own flag.
- `history(limit)` → `registry.history()` serialized via the existing `tool_list` history-block shape.
- Carries a private `BridgeServices` per GUI process; the GUI owns one instance at app start and closes the executor on quit.

**Restart sweep discipline:** when the GUI's services are built, `Registry.sweep_orphans()` runs exactly as for the MCP server. A crashed-GUI run therefore surfaces as `failed` with the binding restart error in the next session — visible in the GUI's Run panel history and via MCP `list`/`status`.

**Cancel is one path:** the GUI's Cancel button is `client_local.cancel(job_id)`. The same call from an agent over MCP reaches the same `Registry.cancel`. Both land on the claim-time `CancelFlag` from D1. There is no longer a `UpscaleWorker.cancel()` — that mechanism disappears when `UpscaleWorker` is retired.

**Concurrency contract (binding, unchanged):** the executor runs ONE job at a time (`max_workers=1`). A 5-file GUI batch enqueues five jobs; the bridge processes them serially. GPU-bound per-file work is therefore never doubled; the GUI Start button re-enables only when the LAST enqueued job reaches a terminal state (or a user cancel clears the queue).

**State directory default:** `build_services()` accepts `state_dir=None` and resolves it from `VIDLIFT_STATE_DIR` or the platform default (§2, `run_gui.py`). The MCP server continues to use the same default. Agents and the GUI see one registry.

## 6. Windows subprocess/console suppression design

The user-visible bug class: every ffmpeg/realesrgan/seconv call spawned from the GUI flashes a console window on Windows. The packaged GUI exe is already `console=False`; the children are not.

**Helper**

`vidlift/_proc.py`:

```python
import os, subprocess, sys

def popen_kwargs() -> dict:
    """Kwargs for subprocess.Popen / subprocess.run suppressing child
    console windows on Windows. Empty dict elsewhere — pure additive."""
    if os.name != "nt":
        return {}
    si = subprocess.STARTUPINFO()
    si.dwFlags |= subprocess.STARTF_USESHOWWINDOW
    si.wShowWindow = subprocess.SW_HIDE
    return {
        "startupinfo": si,
        "creationflags": subprocess.CREATE_NO_WINDOW,
    }
```

**Call sites (and only these)**

- `vidlift/run.py::_subprocess_runner` — replaced with a tiny `_popen_run` that uses `subprocess.Popen(..., **popen_kwargs())` and `communicate()`. Stdout/stderr capture shape stays identical; tests replaying canned output are unaffected because the seam is the runner callback, not Popen.
- `vidlift/engine_ncnn.py::_run_process` — add `**popen_kwargs()` to the `popen_factory(cmd, ...)` call. `popen_factory=subprocess.Popen` continues to be the test seam, so tests on Linux see no kwargs and continue to function.
- `vidlift/subtitles.py` — seconv/tesseract call sites adopt the kwargs.
- `vidlift/classify_sample.py` — idet sample call site adopts the kwargs.
- `vidlift/benchmark.py` — the slice's subprocess call adopts the kwargs.

**What is NOT done**

- No global patching of `subprocess.Popen`. PyInstaller's own build scripts sometimes patch; VidLift does not.
- No `--hide-console` PyInstaller flag change; the GUI exe's existing `console=False` is correct by itself. The `vidlift_cli.spec` keeps `console=True` (CLI builds must keep a console for diagnostics; this matches the sibling's spec comment).
- No `os.system`/`shell=True` paths exist in VidLift; if a future slice introduces one, it must route through `_proc.popen_kwargs()` too. This rule lands in CONTRIBUTING-adjacent docs as a comment in `_proc.py` itself.

**Tests**

`tests/test_proc_no_window.py` asserts: (a) on `os.name != "nt"`, returns `{}`; (b) on a monkeypatched `os.name == "nt"`, the dict has both keys and the correct flag bits; (c) a spy `popen_factory` in `engine_ncnn._run_process` receives a `startupinfo` kwarg on the monkeypatched-nt path. All headless; no real subprocess.

## 7. Engine-selection behavior and fallback policy

The two real engines in tree are exactly:

1. **`NcnnVulkanEngine`** (`vidlift/engine_ncnn.py`) — Real-ESRGAN via the ncnn/Vulkan binary. Currently supports the single pinned profile `live-action` → `-n realesrgan-x2plus -s 2`. GPU-required, model-hash verified, frame-exact chunked, fail-open to a verified 720p HEVC re-encode on `UpscaleError`. This is THE upscale engine.
2. **`StubEngine`** (`vidlift/run.py`) — passthrough stub that copies prepared → mezzanine with no AI pass. Manifest records `engine_simulated: true`. This is the honest fallback and the test engine. `FakeEngine` (raises) is test-only.

`select_engine(request)` — already in tree — governs behavior:

- `"ncnn"` — force real engine; missing binary or models raises `MissingToolError`, hash mismatch raises `UpscaleError` (which `run_file` then handles via fail-open → encoded original-resolution 720p output, manifest stating why).
- `"stub"` — force the stub, no probe.
- `"auto"` (default) — try `ncnn` (resolve binary + models, verify hashes, run the lazy GPU probe frame); on any failure, fall back to stub and record `engine_note = "auto: stub engine (<reason>)"` in the manifest and the JobRecord.

**v0.4.4 GUI behavior on this scaffold:**

- The engine combo items are precisely the three above, in the order `auto / ncnn / stub`. Labels: `"Auto (recommended)"`, `"Real-ESRGAN ncnn/Vulkan (GPU)"`, `"Stub (no AI; encode-only fallback)"`. Internal values match the `select_engine` request strings byte-for-byte.
- The choice persists in `QSettings` (`engine`, default `"auto"`). A stale persisted value (e.g. from a future engine combo) is read as `"auto"` on load — never silently applied.
- The combo is disabled while a run is active; tooltips explain why ("engine is fixed once a batch starts; cancel to change").
- The choice rides `options["engine"]` into the JobRecord and is re-read on the MCP `status` payload (additive `options.engine` read on the GUI for the row tooltip; no new tool surface needed).
- **Fail-open honesty is unchanged:** if the user chose `ncnn` and the engine fails mid-run, the run STILL encodes from `prepared_path` with `fail_open: true`, `engine_simulated: true` on the shipped pixels, and `fail_open_reason` naming the cause. The GUI's row shows "completed (no AI upscale)" via the same `note` text the bridge emits today. The user is never told a real-AI pass happened when it didn't.
- Output size: unchanged by this design — quality-driven size growth is a property of the encode plan (bitrate + verified decode), and `run_file` already documents that. Replacement safety stays OFF by default (v0.4.4 does not change `plan.replace_source` defaults — they are already opt-in and gated by verified output).

## 9. Migration / compatibility risks

- **R1 — GUI becomes a bridge client.** Anyone scripting against the OLD `UpscaleWorker`'s signals (`file_started`, `file_finished`, `file_failed`, `finished`) breaks. No external consumer is documented; the GUI's own tests are the only known user, so this is internal. Mitigation: keep `gui.UpscaleWorker` as a thin deprecated alias for ONE release that delegates to the bridge path with a `DeprecationWarning`; remove in v0.4.5.
- **R2 — `Registry` and the GUI now live in one process.** A GUI crash mid-run leaves a `running` row until the next process starts and `sweep_orphans` runs — exactly the MCP server's existing story, so no new failure class. Documented in §5.
- **R3 — QSettings across platforms.** Different paths per OS; tests must not depend on persistence. `client_local` is indifferent to where the registry lives, and tests pass explicit tmp state dirs.
- **R4 — `RunState.progress["step"]` is already used by the bridge for status.** The GUI's stage label read is read-only; no conflict.
- **R5 — Engine choice persistence.** A user upgrading from a v0.4.3 GUI with no `engine` setting reads the default (`auto`) — backward-compatible.
- **R6 — Subprocess kwargs on test runners.** `_proc.popen_kwargs()` returns `{}` on Linux, so all existing headless tests on Linux are unaffected. The Windows-specific path is exercised via monkeypatch only, never by platform luck.
- **R7 — No `console` flag flip on `vidlift_cli.spec`.** CLI users expect a console; hiding it would be a regression. The CLI build is untouched.
- **R8 — Replace-source safety.** v0.4.4 does not change source-replacement defaults. Output-only-by-default stays the contract; GUI checkbox state remains opt-in and gated by successful verification. (The current GUI does NOT have a replace-source control; v0.4.4 keeps it that way. Introducing one is a separate milestone.)

## Appendix — verbatim seam contracts Forge must not violate

- `select_engine(request ∈ {"auto","stub","ncnn"}) -> (EngineAdapter, note|None)` (`vidlift/engine_ncnn.py`).
- `run_file(..., engine_request: str, cancel, state_box) -> RunResult` (`vidlift/run.py`). The `state_box` seam is the bridge's live-status contract; the GUI uses it via `client_local`, never directly.
- Registry state machine: `queued → running → {succeeded|failed|cancelled}` and `queued → cancelled`; nothing else. Enforced inside `Registry.transition`.
- Heartbeat cadence: `HEARTBEAT_TOUCH_SECONDS = 5.0`, `HEARTBEAT_LOG_SECONDS = 30.0` (`vidlift/run.py`). The GUI's 1 Hz timer is a VIEW cadence, not a heartbeat cadence; do not conflate them in tests.
- `_status_payload` is the single source of truth for both MCP `status` and GUI status. Fork it and Slice 3 is wrong.
- Cancel: one flag per running job, registered claim-time (D1). The GUI's cancel button never touches threads directly.
