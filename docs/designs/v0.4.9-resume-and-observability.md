## 0. Field evidence this design answers (2026-10-27/28, NINJABASE2)

Two anime jobs (Mary and the Witch's Flower, Whisper of the Heart)
were submitted 20:10. Their upscale phases ran **concurrently on one
GPU all night** (~15 min/chunk x 52 chunks each; both crawled). Mary
was GUI-cancelled at 06:00:55 during mezzanine segment 40/52.
Cancel-retention held exactly as designed (v0.4.7 contract): the
23 GB prepared mezzanine, the run log, and the engine workdir with
`chunk_state.json` (~39/52 chunks, ≈10 GPU-hours) survive under
`J:\Complete\.vidlift-runs\Mary and The Witch's Flower (2017) 480p.20261027-201001.*`
— but they are **orphaned**: a new submission gets a new run-id, so
the B.7 checkpoint's `prepared_path` binding never matches and the
work is unreachable (the checkpoint equality proof at
`vidlift/engine_ncnn.py:2010-2017` compares `state["prepared_path"]`
against the NEW run-id-derived path and fails by construction).

Separately, the GUI *looked* frozen for hours while neither job was
stuck: `jobs.json` records state only at start/finish/transitions
(`vidlift/mcp_bridge/registry.py:112-126`), so no mid-run progress
exists on disk for any reader. In-process the GUI's 1 Hz snapshot
DOES see live progress through the state_box seam
(`vidlift/mcp_bridge/tools.py:407-414`), but the visible symptom — a
stage label that reads the same for hours with no advancing numbers —
was real, because the only persisted signal (`last_activity_at`) was
not surfaced and no chunk counter reached any durable surface.

Verified code facts this design stands on (main @ `69aabe2`):

- B.7 checkpoint: `chunk_state.json` fields are
  `{stamp_fps, prepared_path, prepared_total_frames, chunk_frames,
  completed[{idx, count, segment, segment_size}], params{model,
  scale, chunk_seconds}}` — written atomically per chunk
  (`engine_ncnn.py:1933-1976`), validated wholesale-or-nothing at
  `engine_ncnn.py:1978-2053` (any mismatch deletes the workdir).
- Workdir naming is run-id-derived: `_workdir_for`
  (`engine_ncnn.py:2055-2064`) maps
  `<log_root>/<run_id>.prepared.mkv` → `<run_id>.engine-work`.
- Run-id is `f"{base.stem}.{time.strftime('%Y%m%d-%H%M%S')}"`
  (`run.py:1169`); scratch root is `<source.parent>/.vidlift-runs`
  by default (`run.py:1170`); success-only cleanup at
  `run.py:928-997`.
- The bridge executor is **max_workers=1**
  (`vidlift/mcp_bridge/jobs.py:337-352`, constructed at
  `server.py:136` with no override) — one process can never run two
  jobs at once. Last night's concurrency therefore means **two
  processes** shared the GPU (the documented two-registry split: the
  Windows GUI's packaged `%LOCALAPPDATA%` registry and another
  surface, e.g. an MCP server or a second GUI instance, each with
  its own jobs.json and its own single worker). The in-repo queue
  already serializes; the gap is **cross-process** GPU use.
- Heartbeat/step machinery already exists end to end
  (`run.py: run_with_heartbeat` 288-354; `record_step` 1354-1407;
  `record_progress` 1344-1352; engine `_probe_frame_count_alive`
  heartbeat `engine_ncnn.py:1375-1419`,
  `PROBE_HEARTBEAT_SECONDS=5.0`, `PROBE_HEARTBEAT_LOG_SECONDS=30.0`);
  what is missing is **durability**: none of it crosses into
  `jobs.json` between transitions.

## 1. Feature 1 — Cross-run resume claim

### 1.1 The identity problem, stated precisely

Today the checkpoint is bound to the run-id-derived prepared path
(`<run_id>.prepared.mkv`). Run-ids embed a second-resolution
timestamp (`run.py:1169`), so every resubmission is a new identity
and B.7 wholesale-deletes the old work on first contact. That is
correct behavior for *stale* work and catastrophic for *identical*
work. The fix is to key reusability by **content identity of the
pipeline inputs**, not by the run that happened to produce them.

### 1.2 Claim identity: what must match (binding)

A fresh submission may claim retained scratch for the same source
iff ALL of the following prove equal. Every check is cheap
(stat/probe/classification only); any failure or ambiguity falls
through to the clean path and (per the GC rules in §1.6) the
unclaimed scratch is untouched until GC — never trusted partially.

1. **Source identity**: absolute source path equal, `st_size` equal,
   `st_mtime_ns` equal. (Size+mtime is the same trust level the
   house already uses for the benchmark cache; a source re-rendered
   in place at the same second with the same size is accepted risk,
   stated honestly.)
2. **Plan identity** (re-derived fresh by the new run before any
   claim): target, gb_per_hour, output geometry, **the prepare filter
   chain** (deinterlace classification arm included — the idet sample
   verdict is re-run and must produce the same `sample_chain`), and
   the **upscale profile** (`v0.4.8`: live-action | anime — different
   model ⇒ different `params["model"]` ⇒ B.7 already refuses, but
   the claim layer refuses earlier and cheaper).
3. **Prepared mezzanine proof**: the retained `<old_run_id>.prepared.mkv`
   must exist, its probed duration must pass Gate P against the
   source (the same `duration_gate` the engine runs,
   `engine_ncnn.py:1130-1141`), AND — the strong proof — a
   **decode-count** (`nb_read_frames` pass, the same authoritative
   pass as B.1, `engine_ncnn.py:597-648`) must equal the
   `prepared_total_frames` recorded in the retained checkpoint. This
   costs minutes on a feature file but is the only byte-level
   content proof cheap enough to run at claim time, and it replaces
   the prepare entirely (saves both the ~5 min prepare encode AND
   the subsequent count, since the claim and B.1 share one pass).
4. **Checkpoint validity**: the retained `chunk_state.json` must pass
   the EXISTING `_load_checkpoint` validation with **one surgical
   change** (§1.3): prepared-path equality is checked canonically
   against the *claimed prepared file* (the old path), not the new
   run-id path. Params (`model`, `scale`, `chunk_seconds`), stamp
   token, total frames, per-segment existence+size+duration checks
   all ride unchanged.

Why no content hash of the prepared file: prepare is
`ffmpeg ... -c:v ffv1` over a deterministic filter chain
(`run.py:525-572`), but the **container bytes** embed mux metadata
(writing-app string, timestamps) that ffmpeg does not guarantee
stable across invocations/versions. Hashing 23 GB is also minutes
of pure I/O. Frame-count equality plus duration plus source
identity plus plan identity is the honest proof at the right cost;
the B.4 post-reassembly gates (exact frame equality, audio clock
gate) remain the real tripwire for any subtle prepared-content drift
— a drifted prepared file would fail the mezzanine gates and retain
the rejected mezzanine exactly as today (`run.py:1430-1434`).

### 1.3 The surgical engine change (Forge pointer)

`_load_checkpoint` (`engine_ncnn.py:1978`) gains one optional
keyword, `claimed_prepared_path: str | None = None`. When the runner
claims retained scratch (§1.4), it invokes the engine with the
**claimed** prepared path as `prepared_path` (so
`_workdir_for(prepared_path)` resolves to the retained
`<old_run_id>.engine-work` and the checkpoint's `prepared_path`
matches with NO format change). The mismatch-delete-wholesale rule,
the segment probes, and the params equality are byte-identical to
today. When no claim happens (`resume` absent or no retained set
proves out), the engine path is untouched — v0.4.8 behavior bit for
bit.

No checkpoint format change. No new fields. v0.4.7 checkpoints are
readable as-is (§1.7 verdict).

The runner side: `run_file` gains `resume: bool = False` (default
OFF, the v0.4.7 `replace_source` opt-in pattern). When set, after
plan/sample-classify and BEFORE the prepare command
(`run.py:1310-1316`), the runner calls a new
`find_claimable_scratch(base, log_root, *, plan, sample_chain,
profile, tools, run_cmd)` (new function in `run.py`, ~120 lines)
which:

1. globs `<log_root>/<source-stem>.*.prepared.mkv` (run-id namespaced
   glob — the run-id format is pinned at `run.py:1169`, so the stem
   prefix is exact; no cross-source bleed is possible),
2. for each candidate, locates the sibling `.engine-work/
   chunk_state.json`; candidates without a checkpoint or with fewer
   than 1 completed chunk are skipped (nothing worth claiming),
3. applies §1.2 checks 1-3 (source stat, plan equality, duration
   gate, decode-count) — candidates are tried **newest run-id first**
   (lexicographic order on the timestamp suffix is chronological),
   first full proof wins,
4. on success: sets `prepared_path` to the claimed file, records
   `state.resume_claim = {...}` (new additive state/manifest field,
   §1.8), skips the prepare phase (logs
   `resume: claimed <old_run_id> prepared mezzanine + <N> chunks
   (<GPU-hours> equivalent retained)`), and lets the upscale phase
   run exactly as today — the engine finds the checkpoint naturally.

On any proof failure the candidate is left untouched and the next
candidate is tried; zero candidates → clean run with a log line
`resume requested; no claimable scratch found (preparing clean)` —
never an error, never silent.

### 1.4 Claiming UX — tri-surface (the v0.4.7 pattern)

- **GUI** (`vidlift/gui.py`): a `Resume retained work` checkbox on
  the run panel, default OFF, QSettings-persisted like the engine
  combo, riding `options["resume"]` into `enqueue_run`
  (`gui.py:916-924` region adds one key). When a plan batch contains a
  source with retained scratch, the plan detail text names it
  ("retained partial work exists for this file — enable Resume to
  claim it") so the checkbox is discoverable at the moment it
  matters. Deliberately NOT a per-job "resume button": the GUI's
  job rows are views over registry records; claimability is a
  property of the filesystem, and the batch plan view already has
  the per-file detail surface. (Eric decision D1, §4.)

  Stacked-scratch behavior (cancel → resubmit → cancel again):
  the newest proving candidate wins (§1.3 step 3); older sets are
  GC candidates only (§1.6), never merged, never partially claimed.
- **CLI** (`vidlift/cli.py:459-466` is the replace-source pattern):
  `vidlift run FILE --resume` (`action="store_true"`, default off),
  help text: "claim retained scratch from an earlier failed/cancelled
  run of this same file when source, plan, and prepared content all
  prove equal; otherwise runs clean".
- **MCP** (`vidlift/mcp_bridge/schemas.py:38-63`): `resume:
  {"type": "boolean"}` added to `_OPTIONS_RUN`; `jobs.py:_execute_run_job`
  forwards `resume=bool(options.get("resume", False))` into `run_file`
  at the same forwarding site as `replace_source` (jobs.py:211).
  Absent -> False -> v0.4.8 behavior (the bridge's
  absent-defaults rule, same as `upscale_profile`).

The two-registry split stays exactly as documented: resume is a
**filesystem-level** claim keyed to `log_root` (the source's
`.vidlift-runs`, overridable via `--log-dir` / `options["log_dir"]`).
Whichever registry the job runs under, the claim looks at the same
on-disk scratch. MCP-on-minipc can claim NINJABASE2 scratch only if
the minipc mount can see the same paths — it cannot (J: is Windows),
and no attempt is made to blur that; the claim glob and stats run on
the submitting machine's view, honestly named in the docs.

### 1.5 What happens to the claimed scratch on success/failure

- **Success of a claiming run**: the existing success-cleanup
  (`cleanup_run_artifacts`, `run.py:957-997`) is run-id-namespaced
  to the NEW run-id and would NOT touch the claimed old-run-id
  files. That is wrong for resume: after a verified resumed run, the
  claimed prepared mezzanine and workdir are consumed scratch and
  must go. Fix (binding): when `state.resume_claim` records a claim,
  the success path calls `cleanup_run_artifacts(<claimed_old_run_id>,
  log_root)` ADDITIONALLY (same best-effort, log-warning semantics).
  The claimed run's log and manifest stay (house rule: logs/
  manifests are never cleanup candidates).
- **Failure/cancel of a claiming run**: retention contract unchanged —
  everything stays, and the checkpoint now contains the UNION of old
  and newly completed chunks (the engine already seeds
  `completed_records` from reused entries, `engine_ncnn.py:1672-1679`).
  A later resume claims the accumulated total. Correct by
  construction.
- **Concurrent-claim race**: two simultaneous `resume` submissions of
  the same source by two processes could both claim. Guard: at claim
  time the runner creates a sentinel file
  `<old_run_id>.engine-work/.claimed-by-<new_run_id>` (O_EXCL create;
  failure ⇒ another claim owns it ⇒ candidate skipped). Cheap,
  same-filesystem atomic, no lock manager. The sentinel rides the
  workdir; `_load_checkpoint` never sees it as a mismatch (it isn't
  part of checkpoint validation). Best-effort: a sentinel orphaned by
  a power loss is swept by the GC's age rule (§1.6) and, being only
  advisory, costs at most one unclaimable set until then — never
  corruption.

### 1.6 Stale-scratch GC (retention policy)

With resume, retained scratch becomes durable state, which is exactly
what Eric's 23 GB × N can stack into. Binding defaults (Eric decision
D2, §4 — these are the proposed values):

- **Keep newest 2 retained scratch sets per source stem** (a set =
  `.prepared.mkv` + `.engine-work` + `.ocr-work` sharing a run-id).
- **Age floor: never GC anything younger than 7 days**, regardless
  of count (a week-old cancelled run is very unlikely to be resumed,
  but the newest-2 rule usually keeps it anyway).
- Runs at every GUI/server startup (the same place `sweep_orphans`
  runs, `server.py:126-134`) and after every successful cleanup.
- A set whose checkpoint is missing/corrupt OR has zero completed
  chunks is GC-eligible immediately regardless of age (nothing to
  resume; it is pure triage debris — but note: the rejected-
  mezzanine retention path renames to `.prepared.rejected-<ts>.mkv`
  which is NOT matched by the `.prepared.mkv` GC key, so
  diagnostics are never GC'd by this rule).
- GC is delete-by-exact-path per set, logged to the state-dir log,
  best-effort, never fatal. Size cap: deliberately NOT designed in
  (count+age is predictable; a byte cap invites deleting the one
  resumable set Eric wants). D2.
- The `vidlift-prune` surface: CLI gains `vidlift runs prune
  [--dry-run]` reporting what GC would remove. One function in
  `run.py` (`gc_stale_scratch(log_root, keep_per_source=2,
  min_age_days=7) -> list[...]`), shared by startup and the CLI.

### 1.7 Back-compat verdict on Mary's checkpoint

**Claimable: YES**, with one verification gate. The checkpoint format
at the packaged v0.4.7 tag is byte-identical in fields to repo main @
`69aabe2` (`engine_ncnn.py:1939-1955` — `{stamp_fps, prepared_path,
prepared_total_frames, chunk_frames, completed[{idx,count,segment,
segment_size}], params}`), because `69aabe2` IS the v0.4.7 shipped
tree. The claim path needs no format migration. Gate: Forge must
confirm the actual NINJABASE2 installer was built from this tree
(version string in its manifest says v0.4.7; the packaging workflow
pins the tree it builds). If true, Mary's
`Mary ... 480p.20261027-201001` set claims under §1.2 (source
unchanged, profile=anime both times, and the decode-count pass proves
the 23 GB prepared file). Estimated claim cost at her disk speed:
the decode-count of a feature-length FFV1 mezzanine ≈ several
minutes — versus ≈10 GPU-hours re-run. Whisper's set (if retained —
she was not cancelled; if her job is still queued/running, no claim
applies) is untouched by this design either way.

**Honesty note**: if the packaged build proves to be an older tree
(pre-`69aabe2`, e.g. before the checkpoint's segment_size check
landed), `_load_checkpoint`'s KeyError arm wholesale-deletes the
workdir rather than mis-trusting it — today's fail-safe behavior
carries forward, and Mary re-runs clean. The design never weakens
B.7 to widen compatibility.

### 1.8 New state/manifest fields (additive, schema v2 convention)

`RunState.resume_claim: dict | None` =
`{claimed_run_id, prepared_path, chunks_reused_at_claim,
source_size, source_mtime_ns, claim_checks: [list of what proved]}`.
Rides `to_dict()`/`_build_manifest` under `run.resume_claim` exactly
like v0.4.8's `upscale_profile` echo. Absent/None = no claim (old
consumers unaffected).

## 2. Feature 2 — Anti-freeze hardening (observability, not optimism)

The run was never stuck; it was invisible. Two threads: (a) get the
live progress the runner ALREADY produces into the persisted
registry where any reader (a second GUI, the MCP server after a GUI
restart, Eric's phone) can see it; (b) use the resulting heartbeat
as an honest stuck-run signal.

### 2.1 Persisted progress heartbeat (jobs.json carries live progress)

Today: JobRecord persists only `state/started/finished/
last_activity_at` fields (`registry.py:112-126`, serialized at
146-166); the rich `progress` dict lives only in the in-memory
RunState behind the state_box seam and dies with the process.

Design (binding): a **throttled persisted-progress mirror**.

- New persisted JobRecord field `progress_snapshot: dict | None`
  (serialized in `to_dict`/`from_dict`; absent in old files ⇒ None ⇒
  readers treat as "no live detail", additive both directions).
- The executor's worker loop in `_run_job` (`jobs.py:414-470`)
  already touches the registry at transitions; it gains a **1-line
  periodic mirror**: a sidecar timer (or a check inside the existing
  tracked-runner `touch` path at `jobs.py:170-187` — see Forge note)
  that, at most every **10 s** while a job is running, copies the
  RunState's `progress` dict + `current_phase` +
  `last_activity_at` into `record.progress_snapshot` and calls
  `registry.save()` (the existing atomic-save path, `registry.py:
  326-355` — already temp+replace; cost is one small JSON write per
  10 s per running job).
  - Preferred Forge implementation: piggyback on the tracked runner —
    every tracked command already touches the record; add a
    `maybe_mirror(now)` check there plus one timer-thread tick for
    the long stretches where no command boundary falls
    (the decode-count pass and realesrgan chunk runs are exactly
    those stretches). Both paths use the same 10 s throttle.
- GUI consumption: `_consume_running_snapshot` (`gui.py:1040-1096`)
  changes only in its fallback arm — when the in-memory state_box is
  absent (reader process ≠ writer process), the snapshot's
  `progress` key falls back to `record.progress_snapshot` instead of
  nothing. `_status_payload` (`tools.py:416-489`) gains the same
  fallback assignment (3 lines). The stage bar's busy/reset logic is
  untouched.
- What the GUI then shows during upscale, on ANY reader: current
  chunk `chunk_index/chunk_total`, `frames_done/frames_total`, the
  step label and `phase_note` (`record_step` contract,
  `run.py:1335-1388`), and `last_activity_at` advancing — all
  already produced; this design only persists them.
- Registry snapshot semantics note: `Registry._maybe_reload`
  (`registry.py:226-259`) already converges readers on other writers'
  truth by mtime; the persisted mirror makes the GUI's 1 Hz poll
  (`gui.py:995-1017` → `enqueue_snapshots` → `_status_payload`)
  work identically across processes — no watcher, no new IPC.
- Through-phase coverage: the encode and verify heartbeats
  (`_encode_hint`/`_decode_hint`, `run.py:1460-1513`) already mutate
  `state.progress["encode_seconds"]/["decode_seconds"]` and touch
  the state; the mirror picks these up for free. The decode-count
  pass heartbeats through `record_step` every 5 s
  (`engine_ncnn.py:1390-1419`); same free pickup.

### 2.2 GPU serialization — assessment and recommendation

Established facts: the in-process queue is already depth-1
(`JobExecutor(max_workers=1)`, `jobs.py:341-356`); last night's
two-job GPU collision was **cross-process** (two registries, two
workers, one GPU — §0). Within one process there is nothing to fix.

Options assessed for cross-process GPU serialization:

1. **Depth-1 GPU-phase file lock** (recommended): a lock file
   `<state_dir or log_root>/.gpu-phase.lock` (O_EXCL create + holder
   pid/heartbeat, stale after 2× the heartbeat window) acquired by the
   engine at the TOP of the upscale chunk loop and released after the
   mezzanine gate. Probe/probe-count/prepare/encode/OCR stay
   concurrent (encode is CPU-only; the decode-count is CPU-only;
   neither wants the GPU). A second process's upscale **waits**
   (poll + step label "waiting for GPU (held by pid N since T)" —
   surfaced through the SAME progress mirror, so the wait is
   visible, never a silent stall) rather than time-sharing the GPU,
   which is what made both jobs crawl.
   - Cost: while a non-GPU phase of job A runs (encode ~10-20 min),
     the GPU idles even if job B is waiting — but job B cannot prepare
     concurrently *into* the GPU phase anyway under this lock; the
     idle window is bounded by the longest non-GPU phase, and the
     benchmark cache means neither job needs the GPU probe while
     waiting (probe is lazy at selection; selection already happened).
   - Benefit: each job runs at full GPU speed once it holds the lock;
     total wall time for two jobs is roughly HALF of last night's
     time-shared outcome (GPU-bound phases don't parallelize).
   - Honesty: the lock is advisory (O_EXCL on a shared filesystem —
     SMB/NTFS semantics on J: are documented as a Karen validation
     item, §12 T-gpu-3; a filesystem that refuses atomic create
     degrades to a logged WARNING and unlocked execution, never a
     hang).
2. **max_workers=1 everywhere**: already true; does nothing
   cross-process.
3. **Global device mutex via Vulkan**: out of scope — engine-process
   level, not runner level; would require inter-process GPU
   arbitration inside realesrgan itself.
4. **Do nothing + document**: rejected; the freeze LOOK was
   observability, but the crawl was real — two jobs time-sharing one
   GPU is strictly worse than serialized for throughput and thermal
   reasons.

**Recommendation: option 1**, one lock at the engine's chunk-loop
entry, wait-visible through the progress mirror, degrade-open on
exotic filesystems. If Eric wants zero idle-GPU overlap risk he can
keep submissions on one surface (the GUI) — option 1 makes even the
mixed-surface pattern safe. (Eric decision D3: lock scope = per
machine via state dir, NOT per log_root, so the GUI and an MCP
server on the same host serialize against each other.)

### 2.3 Stuck-run detection (honest)

With §2.1's persisted heartbeat, "no activity" becomes real data.
Design: a **surface-only warning state, never an action**.

- New persisted/derived state: when a reader computes
  `now - last_activity_at > STALE_ACTIVITY_SECONDS` (default
  **900 s** = 15 min — comfortably above every legitimate quiet gap:
  the longest silent stretches today are the decode-count (30 s
  heartbeat-logged, 5 s state-touched) and realesrgan chunk
  processes whose output lands at segment reassembly (checkpoint
  write + on_progress every ~15 min/chunk on the field hardware —
  see §0 timings; on slower GPUs a chunk could legitimately exceed
  15 min, hence Eric decision D4: this threshold, or 1200/1800 s).
- GUI rendering: the running row's status cell text becomes
  `running (no activity 22 min)` in the existing yellow used for
  `cancelled` (`gui.py:1100-1117`), and the stage label gains the
  suffix `— last activity 22 min ago`. No auto-cancel, no kill, no
  modal. The heartbeat gap is **data, not proof of hang**: a wedged
  GPU process and a slow-but-healthy chunk look identical from
  outside; the label says exactly what is known.
- MCP: `_status_payload` gains additive `activity_age_seconds`
  (computed, never persisted); agents draw their own conclusions.
- The 10 s mirror cadence bounds the heartbeat's own staleness: a
  GUI crash makes `last_activity_at` stop advancing, which after the
  threshold reads exactly as "worker gone" — the restart sweep
  (`registry.py:464-477`) already closes that as failed on next
  launch; the stuck warning covers the *same-session* case the sweep
  cannot see.

## 3. Out of scope (named, so nobody assumes)

- Cross-phase resume (re-using a finished encode after a failed
  verify) — chunk-scope only, per B.7's original scope statement.
- Auto-resume without the toggle: resume is opt-in per submission,
  matching the replace-source precedent (destructive-side default
  OFF; here the risk is subtler — claiming 23 GB of the wrong thing
  — so the same default applies).
- Migrating or rewriting any existing checkpoint file.
- Any change to retention of logs/manifests/rejected mezzanines.
- GPU temperature/time-slice management below the phase lock.
- Windows *Actions CI budget*: currently exhausted; the ship plan
  (§5) tolerates a delayed installer build — the milestone does NOT
  block on a Windows artifact.

## 7. Top risks

1. **Claim proof false-negative** (the decode-count of a healthy
   prepared file mismatches the checkpoint's recorded total because
   the count pass is nondeterministic on a corrupt/dirty source):
   fall-through is clean run + retained scratch GC'd eventually; the
   failure mode costs time, never data. Mitigation: claim failure
   logs the exact failing check (`claim_checks` in the state).
2. **GPU lock on SMB/NTFS**: O_EXCL semantics over the J: share are
   unproven from this repo; degrade-open is explicit, and Karen's
   T-gpu-3 pins it on the real target before ship.
3. **Mirror write amplification**: 10 s × hours × atomic JSON saves;
   bounded, but filesystem wear on the state dir is named (jobs.json
   is KBs; risk assessed negligible).
4. **Sentinel orphans** after power loss: cost = one unclaimable set
   until GC age-floor passes; never corruption (the sentinel is not
   part of checkpoint validation).
5. **Two claimants** (§1.5 race): sentinel mitigates; residual race
   window is stat-then-create; documented as accepted at this scale.
6. **Registry format drift**: `progress_snapshot` must round-trip
   through old readers — `from_dict` uses `.get`; an old build
   reading a new jobs.json drops the key on its next save (documented;
   matches every prior additive-field behavior).
